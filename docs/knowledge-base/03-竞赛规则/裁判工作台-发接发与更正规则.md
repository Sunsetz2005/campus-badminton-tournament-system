## 2. 引擎实际实现（已核验为正确）

核心在 `src/domain/rules/match-engine.ts`，纯函数、无 IO／时间／随机。

### 2.1 双打每球换位

`applyRally`（`match-engine.ts:424`）：

1. 得分方 `score += 1`；
2. **只有当得分方原本就是发球方**时，才交换该方两人的逻辑 R/L（`swapLogicalCourts`，`:299`）；接发方任何情况下都不交换；
3. 随后 `setServiceOrder(state, winner)`（`:274`）由**发球方当前分数的奇偶**取发球区（偶数→R、奇数→L，`courtForScore` `:216`），再从该方已保存的 `logicalCourts` 反查具体发球员，接发员取对方同名逻辑区。

这一实现不从比分反推四人位置，人员次序保存在 `logicalCourts` 中。

### 2.2 单打发球区

同一个 `setServiceOrder` 只计算一个 `serviceCourt`，同时用于发球方和接发方（`:281`—`:285`）。
即**双方位置只由当前发球方的分数决定**，不会各自用自己的分数。

### 2.3 手动更正后的基线

`CORRECT_LOGICAL_COURTS`（`:702`）在写入新的 R/L 之后**立即重跑 `setServiceOrder`**，
因此交换发球方两人会改变正确发球员，交换接发方两人会改变接发员，羽毛球标记不会留在旧人身上。
该命令要求原因、不改比分，且被 `assertResultUnlocked` 在已提交/已确认时拒绝。

单打不接受双打 R/L 分配：`assertLogicalCourts`（`:260`）对单打直接抛 `singles_has_pair_courts`，
工作台的单打入口改为「一致性核对」说明，不提供把一人随意放到不合规区的功能。

## 3. 本轮新增的验收测试

验收数据 `tests/fixtures/referee-acceptance-trajectory.json`（由需求包 `acceptance/双打验收轨迹.json` 复制进仓库）
是按规则推导的**合成数据**，使用虚拟身份 A1/A2/B1/B2，不含真实学生信息。

`tests/domain/referee-acceptance.test.ts`（7 个用例，全部通过）逐步断言：

| 用例 | 断言内容 |
|---|---|
| 双打九步轨迹 | 每一步的比分、双方 R/L 分配、发球员、接发员、发球区；接发员恒在与发球员同名的逻辑区 |
| 单打 4:3 强制覆盖 | A=4/B=3 且 B 发球 → 双方各自左区；4:4 → 双方右区；5:4 A 发球 → 双方左区 |
| 单打非每分必换 | 1:2 → 1:3 发球权由 A 转 B，但 B 新分数 3 为奇数，双方仍在左区 |
| 更正接发方 | 交换 A 方两人后接发员由 A1 变为 A2，比分不变，下一分以更正结果为基线 |
| 更正发球方 | 交换 B 方两人后发球员由 B2 变为 B1，比分不变，下一分以更正结果为基线 |
| 未确认首发 | 创建后 `servingSide/serverPlayerId/receiverPlayerId/serverCourt` 均为 `null`，不伪造发球者 |
| 单打拒绝双打分配 | 返回 `singles_has_pair_courts` |

**结论：现有引擎与该轨迹完全一致，本轮未发现需要修复的计分或换位缺陷。**
这是「确认既有实现正确」，不是「修复了缺陷」。
