# 计分与双打发接发

本文定义工程模型，不替代最新版竞赛规程和裁判员审阅。21 分、替代 3×15 和单局 21 的参数来自已记录来源，正式启用条件见[规则来源与版本](规则来源与版本.md)。

阶段 2 已在 `src/domain/rules/match-engine.ts` 建立纯 TypeScript 规则引擎；阶段 3 已实现数据库权威状态、计分事务和场地优先裁判工作台。本轮场地图重构及新增回归仍待完整质量门禁和独立复验，真机与真人裁判操作也未测试，不能把本页描述为正式规程采用或现场验收结论。

## 规则依据与显示口径

当前工程口径依据 [BWF《Laws of Badminton》2025-04-26 V5.0](https://extranet.bwf.sport/docs/document-system/81/1466/1470/Section%204.1%20-%20Laws%20of%20Badminton%20-%2026%20April%202025%20V5.0%20(1)%20.pdf) 第 9.1.3、9.5、10、11、12 条实现，仍须经过赛事正式采用和裁判员复核：

- 场地图四格表示**下一次发球前**的规则发球区，不表示回合进行中的实际跑位、前后站姿或战术位置。
- 发球员与接发员必须位于斜对角发球区；双打搭档在不遮挡对方视线的前提下可在各自场区内自由站位，因此界面不据此推断回合中的实际位置。
- 单打由当前发球方和该方比分奇偶唯一确定发球区：偶数从右发球区发球，奇数从左发球区发球；对方位于斜对角接发区。单打没有任意“左右换位”命令。
- 双打仅在**发球方赢得一分**时交换该方两名球员的 R/L 规则位置；接发方赢分取得发球权时不机械交换其两名球员。
- 发现发球区或发接发顺序错误时，更正到正确状态，已经取得的比分保留，不借位置更正回滚比分。

R/L 是球员相对于球网的规则发球区，不是固定屏幕象限。正常视角左侧为 `END_1`、右侧为 `END_2`；屏幕左半场上格为 L、下格为 R，右半场上格为 R、下格为 L。翻转视角等价于整体旋转 180°，只改变本机投影，不改变 R/L、比分或任何比赛事件。

## 抛硬币与后续局

抛币胜方可以选择先发球、先接发球，或选择起始场地；负方选择剩余维度。已经有效确认后，刷新、重连或不满意都不能重抽。第一球前确需作废须裁判长批准并留原因，第一球后不提供普通重抽入口。

后续局不重新抛币；上一局胜方先发。双打可重新确认该方首发球员和对方首接球员。具体流程见[赛事执行规则 v1.0](赛事执行规则-v1.0.md)。

## 必须分开的身份与坐标

| 概念 | 含义 | 哪些操作可以改变 |
|---|---|---|
| Side A / Side B | 整场固定对阵身份 | 比赛创建后不因换边而改变 |
| Player identity | 单打一人或双打四名固定球员 | 合法换人规则另行设计，V1 默认固定 |
| Logical service court | 球员当前在本方左/右发球区的规则位置 | 合法逐分、开局设置、受审计更正 |
| Physical court end | A/B 当前占据场馆哪一端 | 确认物理换边 |
| Screen orientation | 设备将哪一端画在屏幕上方 | 本设备视角翻转，不改变比赛状态 |

双打比分属于 Side/Pair；不能给两名球员各维护一份组合比分。系统只追踪规则意义上的左右发球区，不追踪回合中球员前后跑动或实际站姿。

## 每局开局输入

- 本局首先发球的一方和首先接发球的一方。
- 双打时明确选择首发球员和斜对角首接球员，不得固定为名单第一人；双方另外一名球员据此落入另一规则发球区。
- 单打按首发方、0:0 偶数比分和斜对角关系生成双方位置，不提供任意换位。
- 双方开始时的逻辑左右发球区；确认前只能显示为“拟首发 / 拟首接”草稿，不能冒充服务器已确认状态。
- 双方物理场地端。
- 输入由裁判确认后形成开局事件；不能靠刷新页面重新抽签或重置。

## 纯规则状态机

规则引擎输入是上一权威状态、冻结规则快照和一个合法命令，输出新状态及产生的领域事件；不读取数据库、浏览器或系统时间。

事件重放从初始状态开始逐条重新执行保存的命令，并将重新推导的事件与保存的前后快照、版本、指纹和元数据核对；不把 `stateAfter` 直接当成重放结果。任何快照不一致都拒绝恢复并报告事件损坏。

单双打逐分逻辑必须由比赛冻结的规则快照驱动。传统双打逻辑：

1. 发球方赢回合：发球方加一分、继续拥有发球权，并按规则更新本方发球员/逻辑发球区；接发方不会因为对手得分而自行换位。
2. 接发方赢回合：接发方加一分并取得发球权；不能机械地交换该方两名球员。下一发球员由新比分奇偶、该方当前逻辑位置及开局/历史状态共同确定。
3. 接发球员由发球员、逻辑发球区和球场几何确定，界面明确显示“谁发给谁”。
4. 任何手动位置更正都产生独立事件和原因；之后算法从更正后的状态继续。

上述行为必须通过权威规则和黄金序列逐分核验。不得用“谁得分谁的两人就交换”这一错误捷径。

## 建议状态字段

```text
gameNumber, gamesWonA, gamesWonB
scoreA, scoreB
servingSide, serverPlayerId, receiverPlayerId
sideALeftPlayerId, sideARightPlayerId
sideBLeftPlayerId, sideBRightPlayerId
physicalEndA, physicalEndB
pendingInterval, pendingChangeEnds, gameStatus
version
```

屏幕视角不放入上述比赛快照；它是设备会话偏好。

场地图也不得重新实现上述算法。界面只能投影引擎给出的 `logicalCourts`、`physicalEnds`、`serverPlayerId` 和 `receiverPlayerId`：物理换边只移动队伍及其比分面板所在半场，`score.A` / `score.B` 始终归属于原 Side；本机视角翻转不产生命令、事件或版本变化。

## 黄金序列要求

- 单打从 0:0 到一局结束，覆盖连续得分和发球权转换。
- 21 分覆盖 20:20、29:29；替代 3×15 覆盖 14:14、20:20；单局 21 验证 11 分换边。
- 双打四人逐分序列，覆盖发球方连续得分、接发方多次夺回发球权及 0 分/奇偶切换。
- 在任一分后断言比分、发球方、发球员、接发球员和四人左右位置。
- 在间歇点、换边点、局点、延长和封顶附近执行撤销再重放。
- 手动合法更正后继续得分，确保 reducer 不恢复旧的错误位置。

测试清单见[黄金用例与回归清单](../05-测试验收/黄金用例与回归清单.md)。
