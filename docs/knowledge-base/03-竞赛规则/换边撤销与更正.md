# 换边撤销与更正

纯规则引擎、阶段 3 计分事务及界面预览已经实现下述状态区分、最近可逆得分撤销和追加事件重放。本轮 S2-008 协议收口和场地图交互仍待完整质量门禁及独立复验；已确认结果的完整下游影响图仍属于后续阶段。

## 三种不能混淆的操作

| 操作 | 改变比赛状态 | 改变比分 | 典型用途 |
|---|---|---|---|
| 物理换边 `ConfirmChangeEnds` | 交换 A/B 的场地端 | 否 | 规则触发或人工补做实际换边 |
| 左右状态更正 `CorrectLogicalCourts` | 调整一方/双方逻辑发球区 | 否 | 纠正发现的发接发位置错误 |
| 屏幕翻转 `FlipScreenView` | 否，仅设备偏好 | 否 | 裁判改变观看方向 |

规则触发换边时只创建一个带触发版本的 `pendingChangeEnds`。确认一次交换一次并清除待办；重复确认同一 ID 必须成为幂等重复，而不是再次交换。

若仍有未处理的规则换边义务，裁判授权的 `CORRECT_PHYSICAL_ENDS` 必须通过 `obligationRelationship` 显式说明端位更正与该义务的关系：

| `action` | 现场含义 | 待办处理 |
|---|---|---|
| `FULFILL` | 提交的端位就是现场已经完成规则换边后的最终事实 | 消费所引用的 `CHANGE_ENDS` 待办，不再额外交换一次 |
| `KEEP_PENDING` | 只纠正系统此前记错的当前端位，现场尚未履行本次规则换边 | 保留所引用的 `CHANGE_ENDS` 待办，之后仍须确认实际换边 |

关系对象必须引用当前存在且类型匹配的待办；错误 ID、无待办却附带关系、存在待办却未说明关系都必须拒绝。`PHYSICAL_ENDS_REVIEW` 是“必须核对并落定现场端位”的独立待办，只接受 `FULFILL`，不能用 `KEEP_PENDING` 留存。

旧字段 `fulfillsObligationId` 仅为已持久化历史事件的确定性重放保留，并按 `FULFILL` 解释；新命令和界面不得继续发送它，也不得与 `obligationRelationship` 同时出现。

## 三类位置更正的 phase 门禁

| 命令 | 允许 phase | 其余 phase |
|---|---|---|
| `CORRECT_LOGICAL_COURTS` | `IN_PROGRESS`、`OBLIGATIONS_PENDING`、`PAUSED` | 拒绝 |
| `CORRECT_SERVICE_ORDER` | `IN_PROGRESS`、`OBLIGATIONS_PENDING`、`PAUSED` | 拒绝 |
| `CORRECT_PHYSICAL_ENDS` | `IN_PROGRESS`、`OBLIGATIONS_PENDING`、`PAUSED`、`GAME_COMPLETE`、`AWAITING_NEXT_GAME_SETUP` | 拒绝 |

因此三类命令都不能从赛前状态非法跳转，也不能在特殊结果待提交、普通结果待提交、已提交或已确认状态下直接改写。结果流程确需更正时，必须先走受控重开；受控重开并不自动绕过上表的具体 phase 门禁。

## 撤销最近误录

“更正 −1”进入撤销最近一分的服务端预览流程，不直接执行 `score = score - 1`。界面必须核对预览中被点击一方恰好减少一分、另一方比分不变；若最近可逆得分不属于被点击方，则拒绝确认并引导使用完整更正。确认后追加 `UndoCommand`，引用目标命令并重新计算：

- 当前比分和已完成局；
- 发球方、发球员、接发球员；
- 双打四人逻辑左右位置；
- 局中间歇、换边、局结束和赛点提示；
- 比赛状态和结果提交资格。

原得分事件和撤销事件都保留，审计历史不得被抹去。阶段 2 已固定为：已经被撤销的命令不能再次普通撤销，撤销事件本身不能反撤销；需要重做时发送新的业务命令和新的 `commandId`。

## 非最近一分和规则状态更正

以下情况进入受权限控制的更正流程，而不是普通 `−1`：

- 需要改动非最近一分或多分；
- 发现发球区/发接发顺序错误，但已经发生后续合法得分；
- 新局已经开始；
- 结果已经确认或锁定；
- 更正可能改变名次、晋级或后续比赛参赛者。

更正流程必须保存原因、原状态、拟修改状态、影响预览、申请人、批准人、版本和时间。真实比赛中的发球区错误纠正不等于取消已经取得的分数；具体处理以赛事采用的规程为准。

完整比分状态更正还必须校验：当前局分尚未构成胜局、已完成局与胜局计数一致、比分未越过封顶，以及当前阈值应有的间歇/换边义务与比赛阶段一致。不能把已经结束的局伪装成进行中，也不能静默丢掉阈值待办。

四类 `CORRECT_*` 命令在结果已提交或已确认时统一拒绝，必须先执行受控重开。完整比分更正只允许在比赛进行中、待办处理中、刚结束一局或全场结果受控重开后的待提交状态执行；未抛币、等待开局、等待下一局、暂停和特殊结果状态均不能借比分更正跳转为进行中。

特殊结果录入错误使用 `INVALIDATE_SPECIAL_OUTCOME`。该命令要求原因，只在特殊结果待提交状态可用，并从对应录入事件的前状态精确恢复比分、发接发、位置、待办和原 phase。特殊结果不允许直接覆盖；已提交或确认的结果必须先受控重开再作废。原录入事件和作废事件均保留。

## 已确认结果的影响控制

1. 从目标比赛向排名、晋级席位、已排后续比赛和已开始比赛构建影响图。
2. 在写入前展示受影响对象和可自动重算/必须人工处置的项目。
3. 后续比赛未开始时，可由授权负责人批准后在事务中重算名次和晋级来源。
4. 后续比赛已经开始时，禁止普通自动回写，建立处置事项并由赛事负责人决定。
5. 任何处理都保留旧值、新值、原因和批准链。

锁定后使用 `ResultRevision` 新增版本，旧成绩册标记被替代而不是覆盖同名文件。更正影响未开赛晋级链时先冻结所有受影响节点；后续比赛已经开始或结束时禁止自动换人、抹分或重写历史，由裁判长登记暂停、维持、取消或重赛决定。

## 必测故障

- 在 10:10 得分触发 11 分间歇后撤销，间歇待办应恢复。
- 在决胜局换边点得分并确认换边后撤销，必须明确物理场地如何处置，不能默默翻两次。
- 得分结束本局后撤销，比赛回到进行中且下一局不能保留为已开始。
- 同一换边/撤销命令重复请求只生效一次。
- 手动更正双打位置后继续得分，后续位置以更正结果为起点。
- 同一 `CHANGE_ENDS` 待办分别验证 `FULFILL` 会消费、`KEEP_PENDING` 会保留，且都以提交的端位作为权威现场事实。
- 新旧待办关系字段同时出现、错误待办 ID、无关系裸更正和 `PHYSICAL_ENDS_REVIEW + KEEP_PENDING` 均拒绝。
- 历史 `fulfillsObligationId` 事件经 JSON 往返仍可确定性重放，新写入不再使用旧字段。
- 三类位置更正在每个允许/拒绝 phase 上逐项验证，尤其覆盖赛前、特殊结果待提交、结果待提交、已提交和已确认。
- 已确认结果更正影响晋级者时，未授权用户不能提交。
