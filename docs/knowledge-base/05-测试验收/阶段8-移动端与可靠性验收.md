## 1. 本阶段改了什么

| 类别 | 改动 | 位置 |
|---|---|---|
| 请求伪造防护 | 非 GET 的 `/api/*`（`/api/auth/*` 由 Better Auth 自查）必须来自本站：看 `Origin`，没有时看 `Sec-Fetch-Site`；跨站、`null` 来源 403 `cross_origin_rejected` | `src/proxy.ts`、`src/server/security/request-guard.ts` |
| 请求体上限 | proxy 缓冲上限 4 MB；按 `Content-Length` 超过 4 MiB 直接 413；海报上传先按声明长度拒绝再读表单 | `next.config.ts`、`src/proxy.ts`、海报路由 |
| 公开查询限流 | 进程内固定窗口、按来源：`/api/public/*` 每分钟 600 次；`/public/*` 页面每分钟 3000 次（考虑校园网出口 NAT）；可用环境变量调整，`0` 关闭 | 同上 |
| 安全响应头 | `X-Content-Type-Options`、`X-Frame-Options: DENY`、`Referrer-Policy`、`Permissions-Policy` | `next.config.ts` |
| 日志 | 脱敏字段扩展到邮箱、电话、联系方式、学号、真实姓名；未知 500 此前不记任何原因，现在记错误类型、数据库错误码和截断消息（不记请求体、堆栈） | `src/server/logging.ts`、`src/server/services/errors.ts` |
| 手机局域网登录 | **修复**：Better Auth 只信任 `BETTER_AUTH_URL`，手机用局域网 IP（甚至电脑用 `localhost`）登录都被 403 `INVALID_ORIGIN`。现在生产只信任显式配置（`BETTER_AUTH_URL` + `APP_TRUSTED_ORIGINS`）；开发另信任本机网卡当前的局域网 IPv4 与 localhost（取自网卡，不取自请求头） | `src/server/security/trusted-origins.ts`、`src/server/auth/auth.ts` |
| 公开页新鲜度 | **修复**：公开比赛详情的「最后同步 / 数据更新时间」取的是**赛事**的更新时间，记分后不前进；改为取比赛与赛事中较新者。实时比分页另显示「页面更新于 hh:mm:ss」，断网时写明「显示的是 hh:mm:ss 的数据」 | `public-projection.ts`、`live-match-tools.tsx` |
| 计分区防误触 | 同侧 +1 与更正入口间距由 8px（手机 5px）加大到 14px（手机 12px） | `src/app/styles/workbench.css` |
| 屏幕常亮 | 持有控制权时申请 Screen Wake Lock，状态栏显示「常亮 已开启/未开启/不可用/被系统拒绝」；不可用时给人工替代提示（把自动锁定暂时改为「永不」） | `src/ui/screen-wake-lock.ts`、`scoring-workbench.tsx` |
| 渐进增强 | 应用清单、图标（含 maskable 与 apple-touch-icon）、`viewport`（不禁止缩放）、主题色；**不注册 Service Worker** | `src/app/manifest.ts`、`src/app/icon.svg`、`public/icons/` |
| 事务重试 | 可串行化冲突重试上限 8 → 12（见 §5 基准发现） | `src/server/services/transaction-retry.ts` |

## 5. 小规模负载基准与重启演练

**可复现步骤**：

```bash
pnpm run db:test:prepare
pnpm exec dotenv -e .env.test -- tsx scripts/build-production-startup-test.ts
pnpm exec dotenv -e .env.test -- tsx scripts/reliability/phase8-drill.ts
```

**环境**：Apple M5 × 10、24 GiB、macOS（Darwin 27.0.0 arm64）、Node 24.21.0、PostgreSQL 15.18（Homebrew）；`next start` 生产构建、数据库与压测客户端**同在本机**（没有网络往返，也没有反向代理）。所有读者来自同一地址，相当于校园网出口 NAT 后的一群观众。

**规模**：6 场比赛同时记分（同一裁判账号分别取得控制权），每场开局 + 40 分（含间歇确认）共 258 条命令；公开读者按界面实际间隔每 10 秒读一次比赛详情接口；6 个裁判只读端每 2 秒读一次权威状态。

| 运行 | 节奏 | 公开读者 | 命令延迟 p50 / p95 / 最大 | 命令错误 | 公开读 p50 / p95 | 裁判只读 p50 / p95 | 读错误 | 单个观众看到新比分 p50 / p95 / 最大 |
|---|---|---|---|---|---|---|---|---|
| 持续（默认） | 每场每秒 1 分 | 80 | 29 / 113 / 619 ms | 0 | 10 / 20 ms | 30 / 46 ms | 0 | 5.3 / 9.6 / 10.0 秒 |
| 持续 + 300 观众 | 每场每秒 1 分 | 300 | 28 / 134 / 284 ms | 0 | 4 / 13 ms | 28 / 46 ms | **429 × 940** | 5.0 / 9.5 / 10.0 秒 |
| 持续 + 300 观众，关闭限流 | 每场每秒 1 分 | 300 | 30 / 91 / 350 ms | 0 | 8 / 16 ms | — | 0 | 5.4 / 9.6 / 10.0 秒 |
| 突发 × 3 | 无间隔（约 40 条/秒） | 80 | 27—32 / 298—408 / 2581—4322 ms | 0、1、1 条 500 | — | — | 0 | — |

结果文件在 `artifacts/phase8-mobile/bench/`。「单个观众」口径按每位观众各自的轮询计算；另有「任意一位观众最早看到」口径（持续运行约 0.4 秒），它只说明服务端投影已更新，不代表任何一位观众的体验。

「每场每秒 1 分」已是真实回合频率（约 10—20 秒一分）的 10 倍以上；突发节奏是压测上限，不是现场场景。

**重启演练**（每次运行都执行，全部 6 次一致）：记一分 → SIGTERM 停止生产服务 → 确认不可达 → 重新启动（就绪约 1.4 秒，总中断约 1.7 秒）→ 同一会话 Cookie 仍有效（200）→ 按原 commandId 查询得到该命令结果与版本 → 同内容原样重发返回 `duplicate`、数据库事件数不变 → 同 ID 异内容 409 `command_id_reused` → 过期 `expectedVersion` 409 `conflict` → 用重启前的同一控制令牌继续记分 201。

**过程中发现**：

1. 突发写入时，不同比赛之间也会被 PostgreSQL 可串行化隔离中止（Prisma `P2034`：共享索引页上的谓词锁误报）。原 8 次重试（总退避约 1 秒）每轮约 3/258 条命令变成 500；提高到 12 次后每轮 0—1 条。持续节奏多轮为 0。**安全性不受影响**：事务整体回滚，裁判端把 500 当作「结果未知」，保留原 commandId，对账得到「未找到」后可用原 ID 重试。根治需要调整隔离策略，属于阶段 3 的架构决定，本阶段不改，列为已知限制。
2. 300 名同出口观众时公开接口大量 429。页面刷新走 `/public/*`，这里改为单独的高上限（3000/分钟），避免校园网观众页面被自己的出口地址「限流致死」；日常限流应在反向代理上按真实来源做。
3. 首次运行时我自己的压测命令写法有误（zsh 下 `env $cfg` 不分词，读者数变成 0），结果被丢弃；脚本已改为数值参数非法即报错。

## 6. 已知限制

- 真机、真人裁判、局域网长时间运行、系统级旋转、软键盘遮挡、读屏软件：**未测试**。Chromium 无法模拟 iOS Safari 的软键盘与底部工具栏。
- 屏幕常亮只在 HTTPS 或 localhost 可用；手机经局域网明文 HTTP 时一定不可用，只能按提示手动关闭自动锁屏。
- 只读端是轮询，不是推送：裁判只读端约 2 秒、公开页约 10 秒、现场看板 15 秒。
- 限流是进程内计数：多实例各算各的、重启清零；`x-forwarded-for` 在没有可信反向代理时可伪造。
- 突发写入下的可串行化误报见 §5；高于本基准的规模（更多场地、上千观众、跨网络延迟）未测。
- 未设 CSP；HTTPS、反向代理、正式域名与生产限流仍待部署阶段。
- 领队（学院负责人）页面未纳入五视口矩阵（测试环境没有领队的固定测试身份），仅有既有桌面用例。

## 7. 手机手动验收清单（请用真机补验）

记录时写明：设备型号、系统版本、浏览器、访问方式（局域网 HTTP / HTTPS）、日期与执行人。模拟器截图不能替代。

**准备**：Mac 按[本地启动与手机访问](../07-使用部署/本地启动与手机访问.md)启动 `pnpm dev`，手机与 Mac 同一 Wi-Fi，打开 `http://<Mac局域网IP>:3000`。

1. 首页、每日赛程、比赛详情能打开；竖屏与横屏各看一次，没有需要左右拖动整页才能看到的按钮。
2. 用裁判账号登录（确认登录框聚焦时页面没有被自动放大）。
3. 进入「我的执裁」→ 一场全新比赛 → 取得本机控制权。状态栏「常亮」一项记录显示的是什么；若为「不可用」，按提示把自动锁定改为「永不」。
4. 抛币 → 首局设置 → 连续记 5 分。每次 +1 后比分只在服务器确认后变化；手指按 +1 时不会误触到旁边的「更正」。
5. 点一次「更正」，确认只弹出预览，关闭后比分不变。
6. 横竖屏各旋转两次：比分、发接发标记不变，按钮都可点。
7. 打开系统控制中心开启飞行模式：+1 立即变灰、状态栏显示「离线」、比分停在最后确认值。关闭飞行模式：状态栏回到在线，+1 恢复。
8. 在另一部手机（或平板）用同一裁判账号打开同一场：应为只读；第一部手机每记一分，第二部在约 2 秒内跟上。
9. 第三部设备不登录，打开这场的公开比分页：约 10 秒内跟上；关掉网络时显示「显示的是某时刻的数据」。
10. 让第一部手机锁屏 1 分钟再解锁：页面自动对账，不出现重复加分。
11. 「添加到主屏幕」后从图标打开：能正常登录与记分；退出后再打开需要重新登录属正常。
12. 系统设置里把字体调到最大：工作台按钮文字不重叠、不被截断。

每一项写「通过 / 不通过（现象 + 截图）/ 未测（原因）」。
