## 2026-09-25 R3-003 浏览器注入用例不稳定的排查

执行者 Claude。现象：`tests/e2e/scoring-reliability-injection.spec.ts` 的两条 R3-003 用例（「502」「200 结构不符」）时过时不过，失败都是点击「查询原命令结果」超时，失败时页面已无恢复面板、服务器版本已前进、加分按钮可用。

结论：**测试时序竞态，不是产品缺陷**。依据是失败用例的 Playwright trace（网络与动作时间线）：

1. 注入的 502 在 12989ms 返回；工作台按设计先 `refresh(true)` 取权威状态，再按原 commandId 自动发起一次对账查询 `GET /commands/<commandId>`。
2. 用例的「响应待确认」、待确认记录非空、加分按钮禁用等断言在 12999—13005ms 通过——它们落在「自动对账还没回来」的短窗口里，并没有验证到注入的 404。
3. 用例在 13010ms 把注入开关改成 false；自动对账请求此时才进入 `commands/*` 路由处理器（trace 中紧随其后的是 `continue`，不是 `fulfill`），处理器读到 false 后放行到真实服务器，拿到 200。
4. 工作台正确地按原 commandId 核销命令、清除待确认记录并隐藏面板，之后的点击便永远找不到按钮。

`resetMatch` 残留与 `openAndStart` 时机均已排除：失败轮次中开赛回执已落地（按钮可用、比分 0、无待确认记录），且事件表中该 commandId 恰好 1 条。产品行为全程符合要求：结果未知期间没有显示「已同步」，核销用的是原 commandId。

修复（只改用例，未改产品代码）：

- 抽出 `interceptCommandLookups`：注入期间所有 `GET /commands/<commandId>` 答 404，并记录每次查询的 commandId 与已注入次数。
- 抽出 `expectUnresolvedAfterLookup`：先等到至少一次查询**真的被注入的 404 答复**、界面出现「以原命令重试」按钮与「服务器暂未找到这条待确认命令」提示，再断言状态为「响应待确认」且不含「已同步」、加分按钮禁用、本机待确认记录仍在；之后才关闭注入。
- 意图加强而非减弱：新增断言注入期间所有对账查询都使用同一个原 commandId；关闭注入后手动查询恰好发出一次、且仍是原 commandId；「200 结构不符」用例补上事件表该 commandId 恰好 1 条与待确认记录被清除的断言。
