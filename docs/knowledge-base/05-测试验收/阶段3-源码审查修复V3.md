## R3-001 阈值义务在一局内只触发一次

**修改**：`src/domain/rules/match-engine.ts`
- `MatchState` 新增 `thresholdObligationsIssued: string[]`，记录本局已经生成过的阈值义务 ID。
- 新增 `thresholdObligationSpecs()`：阈值全部取自本场冻结规则快照（`intervalAt` 与 `decidingGameChangeEndsAt` 独立），不写死 11 或 8。
- `applyRally` 改为「本局尚未生成过该阈值义务」且「有一方达到该阈值」才生成，并把 ID 记入已生成集合。
- `confirmSetup` 在每局开局清空该集合，因此第二局的 11 分仍会正常触发。
- `applyReplacement`（完整比分更正）按阈值历史判断：更正后仍在阈值之上的，视为已经发生、不重新生成；更正回阈值之下的，阈值事实随之撤回，再次到达时重新触发；直接跳到「首次跨越点」且本局尚未触发的，必须带上对应义务。
- 撤销沿用原语义：`UNDO_LAST_REVERSIBLE` 恢复目标事件的前状态，已生成集合随之回退；若撤销前已实际换边，仍保留物理事实并产生 `PHYSICAL_ENDS_REVIEW`。

**历史事件兼容（引擎 v1 → v2）**
- `MATCH_ENGINE_VERSION` 由 1 升到 2（`src/server/services/match-state-service.ts`）。
- **历史事件一条都不改写、不删除。** `replayMatch` 在比对时通过 `alignEventToRecordedShape` 把重放结果对齐到该事件记录使用的引擎形状：v1 事件按 v1 形状核对，v2 事件按 v2 形状核对。
- `normalizeMatchState` 把 v1 形状的历史状态补齐：局内比分只增不减，因此「本局是否已越过某阈值」可由当前比分确定重建，不依赖任何被删除的证据。
- `loadVerifiedAggregate` 对 `engineVersion < 2` 的权威快照按 v1 形状校验哈希；快照是派生缓存，在下一次写入时自然升级为 v2，行锁与哈希校验都没有被关闭。

**回归**：`tests/domain/threshold-obligations.test.ts`，15 条。修复前 10 红 4 绿（红灯清单见 `artifacts/r3-review/r3-001-baseline-red.txt`），修复后 15/15 通过。
覆盖单局 21、三局 21 首局与决胜局、3×15 决胜局、领先方保持在阈值、另一方稍后到达阈值、B 方对称、间歇与换边阈值不同、换局重新计算、两类撤销、三类比分更正、完整重放、以及 v1 历史事件重放升级。
断言目标一律是「义务不应被生成」，没有用无条件 `clearObligations` 循环吞掉重复。

## R3-002 历史回执不得让界面降版本

**修改**：新增 `src/ui/authoritative-snapshot.ts`；`src/components/scoring-workbench.tsx` 改为统一入口。
- `parseVersionedStatePayload` 要求 `version` 为非负整数且与 `state.version` 自洽。
- `decideSnapshotAdoption(latestKnownVersion, body)` 是唯一的采用判定：低于已知版本的合法快照返回 `IGNORE_STALE`，结构不符返回 `INVALID_PAYLOAD`。
- 组件内 `applyAuthoritativeSnapshot` 是写入界面快照的唯一入口，刷新、提交成功和按原 commandId 找回三条路径共用它。
- 「命令是否已被处理」由 `classifyCommandResponse` 独立判定：旧回执仍然核销待确认命令，但不写回界面。

**回归**：`tests/ui/scoring-client-reliability.test.ts`（6 条）+ `tests/e2e/scoring-reliability-injection.spec.ts` 的浏览器注入。
注入用例在采样窗口内延迟 `/state`，直接观察倒退本身而不是让轮询掩盖：修复前 30 次采样为 `["2"×6, "1"×24]`，修复后 30 次全为 `"2"`。

## R3-003 明确拒绝与结果未知必须分开

**修改**：新增 `src/ui/command-outcome.ts`、`src/ui/pending-command-store.ts`；重写 `submitEnvelope`、`reconcilePendingCommand`、`retryPendingCommand`。
- 只有 **4xx 且带结构化错误码** 才是 `DEFINITE_REJECTION`，才允许清除 pending。
- 5xx、网络中断、超时、200 但 JSON 无效/缺 `state`/版本不自洽/`commandId` 不符，一律 `UNKNOWN`：保留原 commandId、保持只读、按原 ID 查询或重试，**绝不自动生成新 ID 把同一分补发第二次**。
- 成功响应必须同时通过 `status ∈ {accepted, duplicate}`、`commandId` 相符、`version` 与 `state.version` 自洽三项核对，才允许核销。
- 本机存储全部容错：读取抛错、JSON 损坏、字段缺失都进入**受控恢复**，记录不被清空也不显示同步成功；`setItem` 被拒绝时直接阻止本次提交，宁可拒绝操作也不提交一条事后无法对账的命令。
- 控制代次保护未改动：`not_controller`/401/403 仍然立即转只读，旧设备不能恢复写权限。

**回归**：`tests/ui/scoring-client-reliability.test.ts`（15 条）+ 3 条浏览器注入用例。
修复前：502 与畸形 200 都不出现待确认恢复面板；损坏的本机记录使页面抛出未捕获 `SyntaxError`。修复后全部进入受控恢复，事件表中该 commandId 恰好 1 条。

## R3-004 实际结束时间与提交/复核时间分离

**修改**：`src/server/services/scoring-command-service.ts` 新增 `ENDED_PHASES` 与 `endedAtProjection`。
只有跨越「未结束 → 已结束」时写入 `endedAt`；保持已结束时保留原值（`undefined`，不下发更新）；受控重开回到未结束相位时清除为 `null`。

**回归**：`tests/integration/phase-3-scoring.test.ts` 的 R3-004 子套件，受控时钟只伪造 `Date`、不伪造计时器，并按真实租约分段心跳推进，不凭空跳过租约。
断言 10:00 结束 → 10:05 提交 → 10:10 复核后 `endedAt` 仍为 10:00，`ResultRevision.createdAt` 为 10:05、`reviewedAt` 为 10:10；受控重开不改结束时刻；误记 WO 被作废后 `endedAt` 清空；未开赛的 WO 不伪造 `startedAt`，因此时长无法被编造。
修复前实际观测到 `endedAt` 被提交时间 10:05 覆盖。

## R3-005 手机与平板的实际访问条件

**修改**：新增 `src/ui/secure-command-id.ts`；`scoring-workbench.tsx` 在进入可写界面前检测能力。
- 安全上下文下优先 `crypto.randomUUID()`。
- 非安全上下文（局域网明文 HTTP）缺少 `randomUUID` 时，使用 `crypto.getRandomValues` 按 RFC 4122 第 4 版构造 UUID，并在页面上给出「正式执裁请改用可信 HTTPS」的提示。**没有使用 `Math.random`，没有关闭浏览器安全策略、认证或 CSRF。**
- 两种安全随机源都缺失时 `canWrite` 为 false，页面给出可理解的只读原因，而不是等裁判按加分时抛原始异常。

**回归**：`tests/ui/scoring-client-reliability.test.ts` 的 5 条能力检测用例。
**未验证**：没有连接物理 iPhone/iPad，没有检查防火墙，没有配置 HTTPS 与跨设备认证来源。只修 UUID **不等于** 整个 HTTPS 与登录部署问题已解决。

## 性能追加核验

见 `artifacts/r3-review/r3-performance-replay-cost.md`。
量测显示全量重放成本随事件数超线性增长（100 事件 67 ms），且轮询即使最终判定 `unchanged` 也已付出全部代价。
最小优化：`getAuthoritativeMatchState` 在行锁内先比对 `matches.version`，版本未变且不返回任何状态时直接回答 `unchanged`。轮询路径从 66.8 ms 降到约 2 ms 且不再随事件数增长。
**行锁、事件重放和哈希校验都没有被删除**：写入路径与任何返回 `state` 的读取路径仍然完整重放并校验，并有定向回归断言损坏快照仍被发现。
仍未处理：返回完整快照的读取与每次写入仍是全量重放；并发吞吐未量测。

## 本轮发现的既有记账问题（未擅自修改）

`tests/e2e/phase-3.spec.ts` 每次运行都会无条件重写 `artifacts/phase3-browser-simulated/` 下的 6 张截图，但**不会**更新同目录的 `SHA256SUMS`。

本轮实测：把这 6 个文件还原为 HEAD（`70fff5e`）提交的字节后，`shasum -a 256 -c SHA256SUMS` 仍然 **6/6 FAILED**。
也就是说，**在本轮开始之前**，仓库里这份哈希清单就已经和已提交的 PNG 不一致——上一轮运行 E2E 时重新生成了截图，却没有同步更新清单。这与联合独立验收 F-001 是同一类问题的复发。

本轮处理：运行完 E2E 后已把这 6 个文件还原为 HEAD 字节，**没有**把本轮重新生成的图留在工作区，也**没有**擅自改写 `SHA256SUMS`（改写会让清单为一批无法追溯来源的字节背书）。
建议由用户决定：要么让 `phase-3.spec.ts` 像 `referee-court-shots.spec.ts` 一样用环境变量切换输出目录，要么在重新生成后显式重算并记账。
