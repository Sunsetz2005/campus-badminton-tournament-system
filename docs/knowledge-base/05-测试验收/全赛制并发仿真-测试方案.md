### D-1（已解决）新建赛事没有任何途径获得「裁判长」角色

- 事实：`createTournament` 只给创建者 `ADMIN`、给平台共用裁判账号 `REFEREE`（`tournament-admin-service.ts`）。全仓库除种子 `prisma/seed.ts` 外，没有任何服务或接口写入 `CHIEF_REFEREE` 角色；`referee-account-service.ts` 只开通 `REFEREE`。
- 后果：`CONFIRM_RESULT`/`REOPEN_RESULT`/`INVALIDATE_COIN_TOSS`、强制接管、小组名次确认、排除、人工处置、仅结果复核、出场名单修改，全部要求 `CHIEF_REFEREE`。用 API 新建的赛事**没有一场比赛能复核锁定**，因此不会产生晋级回填、积分榜确认和最终名次——用户要求的「建赛 → … → 复核 → 名次/晋级」全流程在新赛事上走不通。
- 另一个相关约束：`CONFIRM_RESULT` 要求复核人与提交人不是同一用户（`independent_review_required`），仅结果补录的复核也要求「补录人以外」的裁判长。因此至少需要：1 个管理员、1 个平台共用裁判账号、**2 个**裁判长账号。
- 可选做法：
  - **A（推荐）**：先另开一个小任务补上产品功能「管理员为本赛事指定裁判长」（服务 + 接口 + 管理页 + 测试），确认后再开始仿真。这是业务代码改动，不属于本测试；仿真只调用这个新接口。
  - B：仿真的前置夹具在 `_test` 库用一条受控 SQL 只授予裁判长角色，并在报告中标为「非产品路径」。这偏离了「禁止直接写库」。
  - C：不补也不写库，仿真只跑到「主裁判提交结果」，复核及之后全部标为「不可测」。

### D-2 计分配置只能按「赛事」选，不能按「项目」选

- 事实：建赛只有一个 `rulePreset`，写成赛事默认规则；`Competition.ruleProfileRevisionId` 字段存在、抽签发布也会优先读它，但**没有任何接口能设置它**。
- 结论：「传统 21 / 3×15 / 单局 21 分配到不同项目」在同一赛事内**不可测**（没有入口，不写库凑）。
- 可选做法：
  - **A（推荐）**：主赛事用传统 21，覆盖全部五个单项与团体赛；同时并行两个小型「卫星赛事」分别用 3×15 和单局 21（各 2—3 块自己的场地、各 1—2 个项目），与主赛事同一时段、同一服务实例运行，用来覆盖另两种计分配置并检验跨赛事数据隔离。代价是场地不与主赛事共用（场地是按赛事建的）。
  - B：只测传统 21，另两种计分配置标为「不可测」。

| 每条命令的代价 | 每条命令在事务里**全量重放**该场全部事件并比对快照 | `loadVerifiedAggregate` |

| 复核 | `CONFIRM_RESULT` 只能由裁判长会话（需先接管）发出，且不能是提交人；**晋级回填、对抗结算发生在复核锁定时，不是比赛结束时** | `scoring-command-service.ts`、`results-service.ts` |
| 开赛门禁 | 服务端**不检查**计划时间、场地是否空闲、选手是否正在别场比赛；共用账号可在本赛事任何一场开赛。团体小场只要求双方出场名单已交齐 | `authorization.ts`、`match-state-service.ts` |

## 3. 赛事场景（参数全部可配置）

所有数值都是默认值，可由命令行参数或 JSON 配置覆盖；随机过程用固定种子（`--seed`），派生出「报名名单 → 抽签输入 → 每场每球胜方 → 注入点 → 请求延迟」的独立子随机流，任何一项改动不影响其他流，便于复现。

## 4. 完整流程（全部走真实 API）

1. `POST /api/admin/tournaments` 建赛（共用裁判账号模式）→ 设置/阶段推进到报名开放。
2. 报名：个人项目一半走后台录入、一半走 CSV 导入（`imports/preview` → `commit`）、少量走匿名邀请链接 `/api/register/[token]`；团体队伍建队、开通负责人、负责人提交名单（学号、性别、报项）。
3. 审核：逐条审核 + 批量通过；穿插驳回、重复学号等。
4. 报名截止 → 抽签草稿 → 调签 → 发布（每个项目）。
5. 赛程：场地、比赛日、预计时长、名单截止设置 → 自动建议 → 草稿逐场调整 → 处理硬冲突/确认警告 → 发布赛程版本。
6. 赛事进入进行中；团体负责人在截止前盲交出场名单。
7. 执裁（§5 调度器）：取得控制 → 抛币 → 逐分 → 间歇/换边 → 局间 → 结束 → 提交 → 释放控制。
8. 复核：裁判长接管 → `CONFIRM_RESULT`（触发晋级回填/对抗结算）；抽样驳回或重开。
9. 小组名次：全部锁定后裁判长确认（同分须写裁定依据）→ 淘汰签位回填 → 下一轮可开赛。
10. 名次榜单发布、成绩册导出（抽样一次，验证快照一致性）、赛事结束。

## 5. 时间与进度仿真

### 5.1 调度器（模拟「现场」）

- 每块场地一个「场地裁判」协程，持有一个登录会话；它从**系统给出的数据**（「我的执裁」与公开赛程）选择下一场，而不是看脚本内部状态，从而观察系统信息是否足以支撑现场决策。
- 默认是「守纪律的现场」：只有当场地空、四名（或两名）选手都不在进行中的比赛、对阵双方已确定时才开赛；比计划早可提前开（检验 §5.3 情形 6）。
- 「违规模式」只在指定注入点打开：故意在选手仍在别场比赛时开赛、故意在同场地上一场未结束时开另一场，用来观察**系统是否阻止或提示**（预计都不阻止，见 §1）。
- 复核由 2 个「裁判长」协程处理队列；复核延迟本身是延误来源（下一轮要等复核锁定，不只是等比赛结束）。

### 5.2 比赛走向由逐分生成

- 每场抽一个「走向模板」：一边倒 2:0（强方每球胜率 0.7—0.8）、拉锯三局（0.5）、多次 20 平加分（在 19:19 后强制交替几分）、29:29 封顶、决胜局逆转；单局 21 与 3×15 同理。
- 回合间隔：对数正态分布随机；11 分（3×15 为 8 分）间歇、局间休息按规则时长乘以压缩系数后等待，再发确认命令。
- 每场的计划结束与实际结束偏差自然产生，不设固定时长。

### 5.3 必须构造的延误情形与预期

| # | 情形 | 构造方式 | 预期/判定依据 |
|---|---|---|---|
| 1 | 同场地上一场超时 | 指定场地某场强制三局多次加分 | 后续场次 `delayed`、`cause=COURT`；公开赛程只在有据（`evidenced`）时显示延误 |
| 2 | 场地空着但选手在别场 | 兼项选手两项计划时间相邻、前一场拖长 | `cause=PLAYER`；守纪律模式下场地空等；违规模式下系统是否阻止开赛＝**设计未定义**（预计不阻止） |
| 3 | 淘汰下一轮等两场上游，一场拖后 | 半决赛一场正常、一场拖长 + 复核排队 | 下一轮在两场都**锁定**前对阵方不完整、不能开赛；记录「结束→锁定→回填」各段耗时 |
| 4 | 团体某小场拖很久 | 第 3 小场强制长局 | 同对抗后续小场、该队下一轮对抗顺延；`TEAM_OVERLAP` 是否出现 |
| 5 | 延误累积到当天最后一场 | 前两轮系统性超时 | 统计各轮计划/实际偏差与传播；超出比赛日开放时段时系统的表现＝**设计未定义** |
| 6 | 提前结束、场地提前空出 | 一边倒比赛 | 能否提前开赛（预计允许）；改到空场需重新发布赛程版本，验证版本差异与「已开始不可改」 |
| 7 | 团体延误与名单截止 | 前一轮拖后，下一轮名单截止按计划时间已过 | 预计截止**不顺延**：负责人提交得 `409 lineup_deadline_passed`，只能管理员代交并标逾期。是否应顺延＝**设计未定义** |

每种情形记录：是否有延误提示、赛程状态、公开看板与赛程页显示、能否改场/提前开赛、是否出现「同一人同时在两块场地」。

### 5.4 时间压缩及其陷阱

服务器时钟不能加速，压缩只能「缩短比赛内容 + 缩短计划时段」：

- **C8 压缩档**（正确性与并发主力）：`matchMinutes=rubberMinutes=5`（最小值）、`changeoverMinutes=1`、回合间隔约 1.5—2.5 秒、间歇与局间按 1/8 等待，现实 40 分钟的比赛约 5 分钟。
- 陷阱一：**延误阈值固定 5 分钟不随压缩缩放**。在 C8 下一个时段的延误≈阈值，单场超时不一定被标为延误，会制造「漏报延误」的假问题。因此 C8 只用于一致性与并发判定，延误语义只看累积延误（>5 分钟）。
- 陷阱二：名单截止是整数分钟。C8 下设 `lineupDeadlineMinutes=2`，截止前后用秒级时间点各打一次。
- 陷阱三：租约 2 分钟、心跳 30 秒是真实时间，**不压缩**；仿真客户端与工作台一样每 30 秒心跳，只在注入「心跳中断」时停。
- **C3 延误档**：`matchMinutes=15`、回合约 4—6 秒，在 L2 规模上专门跑 §5.3 的七种情形，让延误量级与 5 分钟阈值的比例接近现实。
- **R1 真实节奏对照**：2 块场地、真实回合间隔（12—20 秒）与真实间歇/局间时长跑约 1 小时，与同种子 C8 结果对比延误判定与租约行为是否一致。
- **校准（M3，2026-10-24）**：L1 实测按「回合 15 秒」压缩后一场只要 3.2 分钟（中位），远短于计划时长 5 分钟，42 场全部提前开赛，延误统计失去意义。原因是 15 秒只是击球时长，没有算捡球、擦汗等死球时间。现改为「每球现实 25 秒（含死球）」：两局制约 85 球 ≈ 35 分钟，加间歇、局间 ≈ 40 分钟，与「现实一场 40 分钟」一致。C8 每球 ≈ 3.1 秒；C3 改为现实 40 分钟 ≈ 仿真 15 分钟（每球 ≈ 9.4 秒）。上文的「回合约 1.5—2.5 秒 / 4—6 秒」以此为准。

### 6.7 组合压力时段

在 L3 全规模中段安排约 30 分钟（C8 压缩时间）的「混乱窗口」，同时发生：

- 某学院整体退出：其个人项目选手在多个小组中途退赛/弃权，团体队整队弃赛（预计卡住，见 §6.1）；
- 另一学院在一个尚未抽签的项目（预留一个延后抽签的项目）大面积增补；
- 两块场地故障暂停、比赛「转场」；
- 三条延误链同时累积；
- 同时运行 §7 的并发注入。

窗口结束后判定：数据一致、无人同时出现在两场进行中的比赛、所有比赛最终都有确定去向（或被明确列为「预计卡住」并给出卡住的接口与状态）、名次与晋级与独立重算一致。

## 7. 异常注入（通用与团体）

| 注入 | 方式 | 期望 |
|---|---|---|
| 同 `commandId` 同内容重复提交 | 立即重发 / 并发双发 | 一次 `201 accepted`，其余 `200 duplicate`，事件只多 1 条 |
| 同 `commandId` 不同内容 | 改 payload 重发 | `409 command_id_reused` |
| 响应超时后原 ID 重试 | `x-test-response-delay-ms` + 客户端 1 秒中断 → `GET commands/[id]` 对账 → 重发 | 对账返回 accepted；重发为 duplicate |
| 过期 `expectedVersion` | 用旧版本号发 | `409 conflict`，无事件 |
| 两会话抢同一场 | 同账号第二个 `deviceSessionId` | `409 controller_exists` |
| 同账号复用 `deviceSessionId` 的另一登录 | 第二个登录带相同 ID | 预计静默换发令牌、原设备 `not_controller`——是否可接受＝**设计未定义**，单列记录 |
| 裁判长接管 | `takeover` | 代次 +1，旧令牌命令与心跳都 `409 not_controller` |
| 刷新/断网恢复 | 丢弃本地状态 → `GET state` → 续用 | 状态与服务器一致后继续 |
| 心跳中断 | 停心跳 >2 分钟 | 会话过期；重新取得后代次 +1，旧令牌被拒 |
| 撤销与记分并发 | 同一版本同时发 | 恰好一条成功，另一条 `409 conflict` |
| 比赛结束瞬间并发提交 | 制胜分与另一分/提交同时发 | 恰好一条成功；结束后再记分 `422` |
| 随机延迟与乱序 | 每个请求加 0—800 ms 随机延迟；注入模式下打乱同场两条请求 | 服务端按版本拒绝乱序，不出现跳号 |
| 中途重启服务进程 | 停 `next start` → 重启 | 恢复后原 `commandId` 可找回、继续记分；记录重启窗口内的错误码 |
| 出场名单截止前后提交、修改、重复提交 | 截止前提交/带版本修改；截止后负责人提交；不带版本重复提交 | 截止前成功；截止后 `lineup_deadline_passed`；版本不符 `version_conflict` |
| 名单中同一队员重复上场 | 同一人放进时间重叠的两小场、超过兼项上限 | `400 invalid_lineup` |
| 名单队员与个人项目时间冲突 | 选一个同时段有个人项目的队员 | 预计接受＝设计未定义 |
| 对抗提前决出 | 淘汰对抗 3:0 | 未开始小场记「未进行」；已开始的照常打完计入；小组对抗打满 |
| 同一对抗多小场同时结束、同时复核 | 两个裁判长会话同时 `CONFIRM_RESULT` | 对抗小场比分不丢不重（对阵行锁 + 可串行化） |
| 小场撤销/更正联动 | 对抗已决、已回填下一轮后重开某小场 | 下一轮未开赛：撤回签位并重算；已开赛：`downstream_started` |
| 积分榜同分 | 人为构造（§6.3） | 与独立重算一致 |

## 8. 自动判定（不能只看「没报错」）

1. **逐场重放**：读取 `_test` 库每场全部事件，用 `src/domain/rules/match-engine.ts` 的重放从初始状态推导，与 `MatchSnapshot` 状态、哈希、版本完全一致；`stateBefore/stateAfter` 链首尾相接。
2. **独立期望比分**：脚本端用一份**不复用引擎**的简易计分模型（按目标分、分差、封顶、局数、间歇/换边阈值）维护每场期望比分与待办类型，每条命令后与服务器返回状态比对，最终与数据库逐局比分比对。
3. **事件完整性**：无孤儿事件、事件 `matchId` 与所在比赛一致、每场版本从 1 连续无跳号、`commandId` 全局唯一、每条成功请求恰好对应一条事件。
4. **团体对抗**：按小场锁定结果独立推算胜负、小场/局/分统计与「未进行」集合，与系统记录一致。
5. **排名与晋级**：脚本按《赛事执行规则 v1.0》独立实现个人小组排名链、团体积分榜规则、淘汰签位映射（两组 A1—B2/B1—A2、四组 QF 固定映射）、最终名次（含并列），与系统一致；每类赛务异常发生后都重算一次。
6. **赛程不变量**：用 `startedAt/endedAt` 与上场人员（个人取报名单位成员、团体取 `MatchPlayer`）检查——任何时刻同一选手不在两场进行中的比赛、同一场地不同时进行两场（违规模式下的预期违反单独标注，不计为系统 bug）；最终没有永远停在待开赛的比赛（预计卡住的单独列出）。
7. **数据隔离**：个人项目与团体、主赛事与卫星赛事之间无串号——比赛、事件、名单、积分榜只引用本赛事本项目的报名单位与参赛者。
8. **公开一致性**：抽样时刻比对公开赛程/比赛详情/看板与权威状态（允许公开页 10 秒刷新延迟），并检查公开白名单不泄露学号等字段。
9. **性能与错误**：每类接口的成功率、错误码分布、P50/P95/P99 延迟、5xx 与服务端未处理异常日志、可串行化重试次数（如能从日志得到）、限流 429 次数。
10. **延误统计**：每场计划开始/结束 vs 实际开始/结束的偏差、按轮次与场地的传播图、延误提示的命中与漏报（相对 5 分钟阈值）。

## 12. 实现计划（供审查）

### 12.1 原则

- 仿真对系统的**所有写入只经 HTTP 接口**，与浏览器用的是同一批路由；判定阶段只读数据库（`_test` 库，经 `assertTestDatabaseUrl`）。
- 不改业务代码；仿真中发现的问题只记进报告。若某一步因系统缺口无法继续（例如 §6 的「预计卡住」），脚本记录卡住的接口、请求、响应和比赛状态，然后跳过这一分支继续跑，不写库绕过。
- 每个随机决定都来自 `--seed` 派生的子随机流；运行日志里记下每个注入点的 ID，用同一种子加 `--only <注入点>` 可以单独复现。

### 12.5 需要你在审查时留意的取舍

1. **oracle 与引擎分开**：期望比分、对抗、排名、签表、名次都由脚本按文档独立实现，不调用 `src/domain`；只有「重放与快照一致」这一项用引擎。两边不一致时先查 oracle 是否写错，再判定系统问题。
2. **调度器只看系统给的数据**：下一场选择基于「我的执裁」与公开赛程接口，不偷看脚本内部状态；这样能暴露「现场靠系统信息无法正确决策」的问题，但也会让脚本更慢、更复杂。
3. **「预计卡住」的处理**：遇到时记录并跳过该分支，不让整场仿真失败；这意味着某些项目可能没有最终名次，报告会单列。
4. **规模**：L3 约 300 场比赛/小场，C8 档下真实耗时预计 3—4 小时（含复核排队），R1 约 1 小时。
5. **只读判定会直接查库**：判定阶段需要读事件、快照、签位等内部表；这是只读查询，不违反「禁止写库」。

## 13. 批准时追加的要求（2026-10-23）

本节是方案批准时追加的要求，与前文冲突时以本节为准。各项的「依据」都来自只读阅读代码，仍须实际运行证实。

### 13.1 容量探测（M4b，P-02 最高优先级）

- 节奏：采用最快节奏，没有回合间隔，也没有间歇和局间等待。每场比赛由一个协程连续发出命令，收到上一条的响应后立即发下一条。这与浏览器工作台「一次只在途一条」的行为一致。
- 加压：并发场数按 6 → 12 → 24 → 48 逐级加压，每级稳定运行 5 分钟（或每场至少 200 条命令）。比赛来自一个专用的 `_test` 赛事，全部是单打，事先开好。
- 每级记录：
  - 命令的成功率与错误码分布；
  - P50、P95、P99 与最大延迟；
  - 5xx 的数量，以及**首次出现 500 或重试耗尽时的并发场数**；
  - 服务端日志里未处理的异常。
- 可串行化重试次数：应用目前**不记录**重试次数（`transaction-retry.ts` 没有日志），不改业务代码就拿不到精确值。替代做法是每级前后只读一次 `pg_stat_database`，记录本库 `xact_rollback` 的增量，作为重试次数的**上界近似**。这个增量包含所有回滚，报告里要注明。精确计数需要在业务代码里加一行计数日志，只作为建议列出。
- 结论口径：以 P99 低于 1 秒、零 5xx 作为「可安全支持」的门槛。报告给出满足门槛的最大并发场数，再按「每块场地同时最多一场」换算成场地数。12 块场地是否安全，单独给出明确结论。门槛数值可在运行前调整，调整后写进报告。
- 运行位置：本机与服务器（L3 实例）各跑一次。两次结果分开报告，不合并。

### 13.2 同出口 IP 场景（P-10）

- 已知事实：
  - 公开限流来自 `src/proxy.ts`，按 `x-forwarded-for` 第一个地址，没有这个头时按 `x-real-ip`，再没有就全部记在 `unknown` 下。没有反向代理时，本机所有请求本来就共用同一来源。
  - 登录限流来自 Better Auth 1.7.5，只在生产模式默认开启。`/sign-in*` 与 `/change-password` 每个来源 10 秒内最多 3 次，计数存在进程内存里。
- 场景：使用默认限流，不调高。12 个裁判会话、2 名裁判长、16 名负责人、1 名管理员和 300 名观众共用同一个出口。观众每 10 秒轮询一次公开赛程、比赛详情和看板。
  - 观察登录：开赛前集中登录时有多少次收到 429、恢复需要多久，以及负责人首次登录必须改口令时会不会被同一条规则挡住。
  - 观察公开接口：300 名观众的 10 秒轮询换算下来超过 600 次/分钟，公开接口什么时候开始返回 429，返回 429 的观众页面会怎样表现。
  - 观察额度互相挤占：裁判写接口不在公开限流范围，需要证实它们不会因为观众把额度用完而受影响。
- 对照组：用 `x-forwarded-for` 给每个模拟客户端单独一个地址。这样做只在没有反向代理的本机实例上有效，作用是区分「限流」与「系统错误」。
- 真实代理路径：L3 至少有一次运行要经过 `deploy/nginx/default.conf` 同款 nginx。nginx 用真实对端地址**覆盖**转发头，所以经它进入的全部模拟客户端都只有一个来源，伪造的转发头无效，这才是真实的校园网出口情况。这次运行记录上面三项的实际表现。
- 判定：正常使用被限流挡住时，记为「bug 或设计未定义」，并给出触发条件（同一来源、多少人、多长时间）。是否属于 bug，由用户和组织方根据现场网络情况判断。

### 13.3 浏览器真实操作注入（P-12）

这部分用 Playwright 驱动真实的裁判工作台页面 `/officiating/[matchCode]`，不用 HTTP 模拟。每项记录恢复所需的时间，以及是否需要裁判长介入。

| 操作 | 构造方式 | 读代码得出的预期 |
|---|---|---|
| 误关标签页后重新打开 | 先关闭页面（`page.close()`，不释放），再在同一浏览器上下文里新开一个标签页进入同一场比赛 | 新标签页的 `sessionStorage` 是空的，会得到新的设备 ID，因此返回 `409 controller_exists`。恢复只有两条路：等租约（最长 2 分钟，从最后一次心跳算起）过期后重新取得，或者由裁判长接管。两条路分别计时 |
| 复制标签页 | Playwright 不能直接复制标签页，所以在新标签页加载前把原标签页 `badminton-device:<场次>` 的 `sessionStorage` 写进去，复现浏览器「复制标签页」的行为 | 两个标签页带同一个设备 ID，后取得控制的那个会被当成同一设备续用并换发新令牌。原标签页下一次写入得到 `not_controller`。要记录两个标签页界面上各自显示什么，以及是否会出现两边都以为自己在控制 |

| 恢复时有一条在途命令 | 发命令的同时冻结页面或断网 | 工作台按 `GET commands/[id]` 对账，不重复记分 |

### 13.4 数据库层故障注入（P-11）

- 前提：本机的 PostgreSQL 与其他项目**共用**（Homebrew 服务），**不能重启**它，也不能占满它的连接。
  - 需要重启数据库的注入，只在**独立的数据库容器**上做：本机用 colima 起一个只给 stress 用的 PostgreSQL 容器，服务器上用 L3 Compose 自带的数据库。
  - 连接中断，在共用实例上只用 `pg_terminate_backend` 断开 `datname = 'badminton_tournament_stress_test'` 的连接，而且只断本库角色自己的连接。
- 注入项：
  1. **数据库重启**：比赛进行中重启数据库容器，停机约 10 秒。
  2. **连接中断**：断开应用到 stress 库的全部连接。
  3. **连接池耗尽**：用大量慢请求（并发复核加成绩册导出）占满应用池。应用池是 `pg` 默认的 10 个连接，取连接不设超时，所以预计请求会排队等待而不是快速失败。另外在独立容器上把 `max_connections` 占满。
- 每项记录：
  - 故障期间的错误码与延迟；
  - 恢复后应用能否不重启就自动恢复；
  - 故障前后发出的 `commandId` 经对账和重发后，是否恰好产生一条事件（幂等）；
  - 比赛快照与重放是否一致；
  - 有没有命令卡在「已提交但客户端不知道」的状态后被重复记分。

### 13.5 压测端与被测服务分离

- L3 的压测端在本机，被测服务在服务器上，二者分开。请求经 SSH 隧道转发，或经服务器上的 nginx 入口。隧道本身带来的往返延迟在运行前单独测一次（空请求的 RTT），报告中的延迟要同时列出原始值和扣除基线后的值。
- L1、L2 以及本机容量探测时，压测端和服务在同一台机器上。这时每 5 秒采样一次两边进程的 CPU 和内存，`next start` 进程与仿真进程分开统计，同时采样系统负载。报告中要注明「同机运行，延迟数据可信度有限」，并标出采样期间 CPU 是否接近饱和。
- 在服务器上运行时，用 `docker stats` 采样容器的 CPU 和内存，同时采样本机压测端。如果压测端 CPU 持续高于 80%，这一级的延迟数据标为「不可信」。

### 13.7 问题优先级

- 报告里的每个问题都打两项分，各 1—4 分：

### 13.9 裁判规模与轮换（2026-10-23 追加）

#### 系统里「具名裁判」与「共用裁判账号」的关系（已从代码确认）

裁判模式按赛事设置（`Tournament.refereeMode`），两种模式**互斥**，可以切换（`updateRefereeMode`；切到逐场指派时，会吊销没有指派的控制会话）。

| 实体 | 共用裁判账号模式 `SHARED_ACCOUNT` | 逐场指派模式 `PER_MATCH` |
|---|---|---|
| 「具名裁判」是什么 | **不存在**。所有人用同一个用户名登录，系统里只有这一个 `User`（`createRefereeAccount` 开通，或平台共用账号） | 每名裁判是一个独立的 `User`，由管理员经 `POST /api/admin/tournaments/[slug]/referees` 开通，口令只返回一次，不要求首次登录改口令 |
| 逐场指派 | 赛程建议**不分配裁判**，也不提示「尚未指派裁判」（`refereesRequired=false`）；开赛不检查指派（`coveredByAssignment` 恒为真） | `OfficialAssignment(userId, MAIN_REFEREE)`；自动建议按「主场场地 + 忙闲 + 负荷」分配；取得控制必须有本场的有效指派 |
| 赛程冲突「同一名裁判同时执裁」 | 没有指派，所以永远不会触发 | `REFEREE_OVERLAP` 是**硬冲突**，会阻止发布 |
| 延误链 `cause=REFEREE` | 没有指派，所以永远不会出现 | 沿 `OfficialAssignment.userId` 顺延 |
| 比赛记录里的执裁人 | `MatchEvent.actorUserId` 全是同一个共用账号；能区分的只有 `scoringSessionId`，也就是设备 | 是本人的 `userId` |
| 临时换裁判 | 不需要，任何人拿共用账号都能接着打 | 裁判长调用 `POST .../schedule/matches/[matchCode]/referee`（必须写原因），**进行中的比赛也可以换**。同一事务内停用原指派、启用新指派、吊销本场全部活动控制会话；新裁判若正在执裁另一场进行中的比赛，返回 `409 referee_busy`；与已发布赛程时间重叠的情况只提示、不拒绝 |

结论：「44 名具名裁判轮换」只能在**逐场指派模式**下用 44 个独立账号实现。共用账号模式下，系统无法知道是哪名裁判在执裁，按要求标为**设计未定义**，并评估对赛后追溯的影响（见下）。两种模式都要跑，用同一种子分两次运行，不在一次运行中途切换模式。卫星赛事固定用共用账号模式，继续承担「同一共用账号跨赛事执裁」的检验。

#### 场景设定

- 裁判人数可配置，默认 L1 = 6、L2 = 20、L3 = 44。仿真内部维护「裁判（人）」实体：姓名、所在位置（休息区或某块场地）、手上的设备、执裁记录。
- **逐场指派模式**的排班流程：
  1. 开通 44 个账号；
  2. 运行自动建议（`assignReferees=true`）；
  3. 人工调整草稿：把约 10% 的场次改给另一名裁判，并故意制造 2 处 `REFEREE_OVERLAP`，验证发布是否被拦截，之后再改正；
  4. 发布。
- 轮换节奏：每人执裁 1—2 场后下场休息，休息时长按压缩档随机，然后去另一块场地。
  - 逐场指派模式下，「下一场由谁执裁」**以系统指派为准**。调度器只决定「这个人什么时候到场」：按系统里的指派等人，人不到场就不开赛。
  - 共用账号模式下，由仿真自己的轮换表决定谁上场，系统不知道。
- 统计（只统计、不判错）：每人的执裁场数、最长连续执裁场数、休息间隔分布，并与自动建议的分配做对比。
- 设备模式（两种模式下各跑一次）：
  - **场地固定设备**：每块场地一台「平板」，也就是一个固定的登录会话加浏览器存储。
    - 共用账号模式下，下一名裁判直接沿用这台平板的会话和设备 ID，交接时什么都不用做。
    - 逐场指派模式下，平板交接需要退出上一个人的登录，再由下一名裁判用自己的账号登录。设备 ID 按场次存放，新比赛会生成新的 ID。要记录交接耗时。
  - **个人设备**：每名裁判一台「手机」，随人移动。
    - 共用账号模式下，同一共用账号会同时有 44 个 Better Auth 登录会话，大多数处于空闲状态。
    - 逐场指派模式下，是 44 个账号各一个会话。
- 登录与会话：
  - 开赛前约 10 分钟（C8 档下对应真实时间约 75 秒）内，44 人集中登录，与 §13.2 的同出口条件叠加。按 10 秒 3 次的登录限流推算，集中登录必然遇到 429，需要实测恢复时间和最终全部登入的耗时。
  - Better Auth 没有配置登录会话的数量上限，登录会话有效期是默认的 7 天，不随压缩档缩放，所以「空闲登录会话过期后重新登录」无法在运行中自然发生。改为用「退出登录后重新登录」和「清空 Cookie 后重新登录」来代替，并在报告中注明。
  - 控制租约（2 分钟）的空闲过期可以自然触发，照常测试。
  - 记录同一时刻在线的登录会话数和活动控制会话数的峰值。

#### 裁判相关异常（并入 §7 注入表，只在逐场指派模式下有意义的单独标出）

| 异常 | 构造方式 | 预期与判定 |
|---|---|---|
| 裁判上一场拖长，耽误下一场（逐场指派） | 让某名裁判的前一场强制打满三局并多次加分，同时把他下一场安排在相邻时段的另一块场地 | 下一场显示延误，`cause=REFEREE`；对比系统提示的预计开始时间和实际开始时间，并统计由裁判造成的延误占比。这类情形同样受 5 分钟阈值的陷阱影响（§5.4），延误语义只在 C3 档下判断 |
| 赛前换人（逐场指派） | 裁判长在开赛前换人 | 原裁判拿不到控制权；新裁判可以正常取得 |
| 中途换人，同一台设备交接（逐场指派） | 裁判长换人；平板退出原裁判，新裁判登录后继续 | 原会话被吊销，新裁判取得控制时代次 +1，比分不丢；之后的事件 `actorUserId` 是新裁判 |
| 中途换人，换设备接管（逐场指派） | 新裁判用自己的手机进入 | 同上；原手机之后的写入得到 `not_controller` 或无指派 |
| 中途换人（共用账号） | 只换「人」，不在系统里操作；或者换一台设备 | 同一台设备：系统看不出有任何变化。换设备：新设备返回 `409 controller_exists`，只能等租约过期或由裁判长接管。哪一种都无法在系统里记下是谁执裁，**设计未定义** |
| 裁判带着个人设备离场，控制权交给接替者 | 三种方式各测一次：① 离场前主动释放；② 不释放，等租约过期；③ 裁判长接管 | 分别记录从离场到接替者第一条命令被接受的耗时；预计 ①≈立即，②≤2 分钟，③取决于裁判长队列 |
| 交接时还有没完成的待办 | 在间歇待确认、换边待确认、比赛结束但还没提交这三个时间点交接 | 接替者从 `GET state` 中能看到同一项待办，并能完成它；不能出现待办丢失或被确认两次的情况 |
| 指派冲突 | 草稿中把同一人排进时间重叠的两场后发布 | `REFEREE_OVERLAP` 作为硬冲突拦截发布（逐场指派）；共用账号模式下没有这项检查 |
| 换上的人正在别场执裁 | 中途换人时，故意选一个正在执裁另一场进行中比赛的裁判 | `409 referee_busy`；如果只是与已发布赛程时间重叠，系统只提示、不拒绝，记录这一表现 |

#### 判定补充

1. **同一名具名裁判不同时执裁两场**：以仿真内部的「人」为准，任何时刻同一人只在一场进行中的比赛里执裁；仿真自身的轮换逻辑出错时，算作脚本错误。逐场指派模式下再用系统数据核对一遍：按 `MatchEvent.actorUserId` 与 `occurredAt` 构造每个账号的执裁区间，两两之间不能重叠。共用账号模式下这项系统侧核对**无法进行**，标为设计未定义。
2. **执裁人与实际一致**：逐场指派模式下，每场比赛按时间切分的 `actorUserId` 序列，必须与仿真记录的「谁在什么时间执裁」一致，中途换人的切换点也要对上，误差不超过一条命令。`ResultRevision.actorUserId`（提交人）要等于提交时实际在场的裁判。共用账号模式下标为**设计未定义**。
3. **追溯影响评估（共用账号模式）**：赛后只能定位到「哪台设备」（`scoringSessionId → deviceSessionId`）。场地固定设备时，设备和人没有对应关系；个人设备时，也要靠线下登记才能对上人。报告中要写清：争议判罚、错记比分、违规操作发生后能追到哪一层，以及需要哪些线下记录（比如纸质执裁签到表）才能补上。这部分只做评估，不改实现。
4. **报告新增「裁判轮换」一节**：包括各裁判执裁负荷分布（场数和总执裁时长）、最长连续执裁和休息间隔、延误中由裁判造成的比例（仅逐场指派模式）、交接耗时（按方式与设备模式分列）、登录会话与控制会话的峰值、集中登录的 429 次数与全部登入耗时。
