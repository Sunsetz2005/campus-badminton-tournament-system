## 你的角色

你是本项目阶段 3 场地图工作台的**独立验收人**，不是修复者。你的任务是从规则原文、代码、数据库事实、HTTP 行为和真实浏览器行为五个层面攻击性验证本轮改造，并留下可复现证据。

改造前基线固定为 Git commit `c9e6b00`。先用 `git rev-parse c9e6b00^{commit}` 解析并在报告记录完整 SHA；不要把当前 `HEAD`、开发者自述或现有测试通过当成验收结论。审查对象是 `c9e6b00` 到当前工作树的全部已跟踪和未跟踪实现。

最终只允许给出以下三种总判定之一：

- **通过**：规则、状态完整性、权限、安全写入和核心无障碍均未发现阻塞问题，S2-008 与 S2-009 分项复验均通过。
- **有条件通过**：仅存在边界清楚、不影响比分归属、规则正确性、权限、事务和恢复能力的 P3 问题，并明确列出剩余人工或真机门禁。
- **不通过**：出现任何 P0/P1/P2、测试被删除/跳过/弱化、权威状态与画面不一致、S2-008 或 S2-009 未通过，或关键链路无法取证。

未执行、环境不具备或证据不足的项目一律写“未测试/无法确认”，不得写“通过”。

### 双打独立黄金轨迹

使用 A1/A2 对 B1/B2，初始 A1(R) 发、B1(R) 接，独立执行以下得分序列：A、A、B、B、A、A。每一分后逐格记录并断言：

|---|---|---|---|---|

### 换位、换边、撤销和更正

独立执行并取证：

- 双打“更正本方换位”只交换被选方 R/L，不改另一方、比分、物理端或比赛阶段；没有原因或未预览不得写入。
- 手动换位后继续得分，下一次自动轮转仍符合黄金规则，不能形成重复运动员或丢失发接发身份。
- 物理换边只交换 `physicalEnds`，不改变 `logicalCourts`、比分归属或本机视角。
- 撤销最近一分恢复比分、发接发、R/L、物理端、义务和局结束状态；响应到达前画面不得乐观变化。
- 三类更正命令 `CORRECT_LOGICAL_COURTS`、`CORRECT_SERVICE_ORDER`、`CORRECT_PHYSICAL_ENDS` 分别跑完整 phase 门禁矩阵。赛前非法状态、特殊结果待提交、`SUBMITTED`、`CONFIRMED` 必须拒绝；合法活跃状态不能被误伤。不要假设三类命令的允许 phase 完全相同，以代码契约和业务含义分别验证。
- 发球区/顺序更正保留已有比分，非法更正被拒后聚合、版本、事件、快照和审计不得半更新。

## 单独复验 S2-008

不得沿用开发者用例。自行构造一个同时存在 `CHANGE_ENDS` 待办的权威状态，直接验证新协议：

```ts
obligationRelationship: {
  obligationId: "<实际 CHANGE_ENDS 待办 ID>",
  action: "FULFILL" | "KEEP_PENDING"
}
```

必须覆盖：

1. `FULFILL`：现场已换边，按提交值更正 `physicalEnds`，只消费目标 `CHANGE_ENDS`，其他待办保留。
2. `KEEP_PENDING`：只纠正此前端位记录，目标 `CHANGE_ENDS` 仍待执行；之后再确认换边时只交换一次。
3. 错误 ID、非 `CHANGE_ENDS` 待办、无待办却声明关系、缺少关系、以及新旧字段同时出现均拒绝且零写入。
4. 历史事件中的旧 `fulfillsObligationId` 只用于重放兼容；旧事件经 JSON 往返仍确定重放，但新 HTTP 命令不能借旧字段绕过新语义。
5. 同一 `commandId`、同一关系重复提交只产生一次事件；同 ID 改为另一 action 必须 `command_id_reused`，不能覆盖原结果。
6. UI 中“确认已换边”和“只纠正端位但保留待办”若均可达，文案必须让裁判能区分；如果产品只暴露其中一条，报告说明另一条合法通路如何安全进入，不要默认纯引擎存在就等于可用。

报告必须有独立的“S2-008 复验结论：通过/部分通过/不通过”，并给出事件数、待办前后、端位前后和重放结果证据。

## 单独复验 S2-009

自行从进行中的非零比分记录一个错误 `RET`，再用 `INVALIDATE_SPECIAL_OUTCOME` 作废。必须覆盖：

1. 原 `RECORD_SPECIAL_OUTCOME` 事件保留，作废事件记录正确的 `invalidatedCommandId`，不得删除或覆盖历史。
2. 精确恢复该记录事件的 `stateBefore`：比分、局数、发球方、发球员、接发员、R/L、物理端、待办、暂停来源和原 phase 全部一致，不能硬编码回 `IN_PROGRESS`。
3. 分别从进行中、暂停、待办和赛前可合法记录特殊结果的状态进入并作废；每一种都核对原状态恢复。
4. `SPECIAL_OUTCOME_PENDING_SUBMISSION` 不能直接用另一条 `RECORD_SPECIAL_OUTCOME` 覆盖；必须先作废。
5. 在 `SUBMITTED`、`CONFIRMED` 直接作废必须拒绝。经有审计的 `REOPEN_RESULT` 后，裁判长可作废并恢复；实际角色必须记录为 `CHIEF_REFEREE`。
6. 原命令和作废命令分别验证同 ID 同载荷重试、同 ID 异载荷复用、JSON 往返与完整事件重放。
7. 通过真实 HTTP 和测试数据库再走一遍，确认事件、快照、比赛版本、局分投影、结果修订和审计同一事务提交；任一步故障均不得留下半更新。
8. 作废后能继续正常计分，刷新/另一设备看到一致状态，页面不残留 RET/WO/DSQ 标记。

报告必须有独立的“S2-009 复验结论：通过/部分通过/不通过”。该结论不能被阶段 3 其他测试通过所替代。

## 攻击减分、并发、权限和恢复链

### 减分安全

- 点击任一方 `−` 只能打开撤销预览，不能直接减分，不能生成事件，也不能改变版本。
- 服务端预览前后必须证明最近一个可撤销得分确实属于被点击方；若最近一分属于另一方，拒绝确认并保持零写入。
- 取消抽屉、Escape、点击关闭后均无写入；重新打开不能复用过期预览。
- 确认撤销必须使用同一规则引擎，恢复完整关联状态而非只做 `score - 1`。
- 快速双击、触摸后紧接 click、按住、Enter 连按时，一次用户动作最多提交一条命令；全局单一在途锁期间其他写按钮不可再次提交。
- `+1` 在服务器 accepted 前不得乐观改变比分、位置或羽毛球标记；冲突、离线、响应未知和失控时停留在最后确认状态。

### 权限与控制租约

通过真实 HTTP 至少验证：

- 被指派主裁判可取得/恢复控制、记分、撤销、未提交前更正、记录或作废特殊结果、提交结果。
- 只具有 `ADMIN` 的账号、未指派裁判、仅知道比赛 URL 的账号均不能写入、接管或复核。
- 同一管理员只有在服务端确认其 `CHIEF_REFEREE` 实际角色时，才能强制接管、退回/锁定结果或受控重开；审计必须记录实际使用角色，不能笼统记 `ADMIN`。
- 两设备以同一版本同时加分只有一条成功；旧租约、旧设备、旧代次、错误会话和过期令牌均返回明确的 `not_controller`/冲突语义并立即只读。
- 心跳按服务器时间续租，租约过期后旧设备不能恢复写入；裁判长接管原子撤销旧会话、增加代次并建立新会话。
- 所有响应禁止缓存且不泄露控制令牌、内部账号或其他比赛信息；401、403、409、422 语义与正文一致。

权限探针创建的临时角色、会话和审计必须在测试内回滚或可靠清理。不得为了测试而永久修改 seed。

### 幂等、事务与篡改

独立验证并记录数据库前后计数：

- 相同 `commandId` + 相同规范化内容并发提交，只产生一条事件；后续返回 `duplicate` 和原持久化结果。
- 相同 `commandId` + 不同内容返回 `command_id_reused`，版本与所有投影不变。
- 两条不同 ID、相同 `expectedVersion` 的并发加分只有一条 accepted，另一条 conflict 并附权威版本。
- 事务中事件、快照、`Match.version`、`Game`、`ResultRevision`、租约和审计任一步注入失败时全部回滚。不要只看 HTTP 500；直接查表证明无半更新。
- 从锚定初始状态和所有持久化事件能重建当前聚合；篡改初始状态、事件载荷、`stateBefore`、`stateAfter` 或任一哈希后，后续写入必须失败关闭。
- `Match.version`、快照版本、最后事件版本和状态哈希始终一致，事件只追加不覆盖。

### 响应未知恢复

仅在显式测试开关开启且数据库名以 `_test` 结尾时使用响应延迟注入，制造“服务端已提交、客户端未收到响应”：

1. 发送前检查浏览器已保存完整待确认命令，包括稳定 `commandId`、正文、会话和代次。
2. 让客户端请求超时或断线，但确认数据库实际只提交一次。
3. 刷新、恢复联网或页面重新可见后，客户端必须先查询原 `commandId`。
4. 查到时恢复原持久化结果；查不到时只允许用**同一完整命令和同一 ID**重试，绝不能自动生成新 ID。
5. 对账完成前界面保持“响应未知/只读”且停留在最后确认状态。
6. 生产启动时开启该测试开关必须被拒绝；非 `_test` 数据库也必须拒绝，不能仅靠隐藏请求头。

## 浏览器、响应式和无障碍验收

必须使用真实 Chromium 页面和真实 HTTP，不用静态 HTML 截图替代。至少覆盖：

| 场景 | 视口/设置 | 必查内容 |
|---|---|---|
| 手机竖屏 | 390×844 | 横向球场完整可理解，双方比分不纵向堆成长页，主操作可达 |
| 窄屏手机 | 375 CSS px | 无关键裁切、重叠或横向页面溢出 |
| 平板横屏 | 1024×768 | 首屏容纳紧凑状态栏、完整球场、换位/换边和主比分操作 |

| 辅助偏好 | reduced motion/transparency、high contrast | 无依赖动画或透明度的信息丢失，焦点和边界仍清楚 |

逐项检查：

- 触控目标至少 48×48 CSS px，比分按钮至少 56×56 CSS px；以浏览器计算后的边界盒取证。
- A/B、姓名、队伍、R/L、物理端、发球/接发、联网、控制权和同步状态都有文字，不依赖颜色。

- 受控抽屉支持初始焦点、Tab/Shift+Tab 不逃逸、Escape 关闭、错误关联、键盘确认和焦点返回；背景不应在模态状态下继续写入。
- 网络、控制权、命令同步是三个独立文字状态；离线、提交中、响应未知、版本冲突和失去控制的原因不能混成一个模糊标签。
- 前台每 2 秒附近拉取、后台降频；重新可见、恢复联网和旋转后先拉权威状态。心跳失败、浏览器离线或命令超时立即只读。
- 位置变化只使用静态切换或短 `transform`/`opacity`，没有拖拽依赖、长按连发、无意义弹跳或动画库。

完成单打和双打各一组手机竖屏、平板横屏截图。报告中明确写“Chromium 浏览器设备模拟”，不得写成真机证据；真机和真人裁判仍标记未测试。
