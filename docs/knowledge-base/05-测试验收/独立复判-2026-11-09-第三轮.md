## 3. 逐项细节

### 3.1 RV2-01：离场待续时的特殊结果

**全链路**（探针 R3-OUTCOME、R3-CHAIN、R3-AFTER-RET）：

- 四种特殊结果在离场待续（暂停中、无场地、有标记）时都被接受，比赛转为结束待提交，标记保留、仍无场地。开发用例只测了退赛。
- 退赛 → 提交（待复核）→ 裁判长确认（`SUBMITTED` + `LOCKED`，标记仍在）→ 重开（回到结束待提交）→ 作废特殊结果（回到暂停中，标记仍在）→ 恢复被拒 `match_awaiting_court` → 转场到空场地（标记清除）→ 恢复成功，比赛进行中、在新场地上。确认结果时 `settleAfterResultChange` 在同一事务里执行，没有因标记出错。
- 退赛后：作废计分被拒（409 `match_awaiting_court`，不是 500）；完整比分更正被引擎拒绝（422，特殊结果待提交不可更正）；转场被拒（409 `match_not_suspended`）；普通撤销不适用于特殊结果（422 `nothing_to_undo`，特殊结果走作废）。

**有没有命令能让带标记的比赛回到进行中或未开打**（逐个核对 `submitScoringCommand` 与引擎）：

| 起点（带标记） | 命令 | 结果 | 依据 |
|---|---|---|---|
| 暂停中 | `RESUME_MATCH` | 409 `match_awaiting_court` | `assertHasCourtToResume` |
| 暂停中 | `VOID_MATCH_SCORING` | 409 `match_awaiting_court` | 第一轮修复，未变 |
| 暂停中 | `CORRECT_SCORE_STATE` / `UNDO_LAST_REVERSIBLE` | 引擎拒绝 | 第二轮探针，仍通过 |
| 结束待提交 | `INVALIDATE_SPECIAL_OUTCOME` | 回到暂停中，放行 | `assertCanReoccupyCourt` 对 `SUSPENDED` 直接返回 |
| 结束待提交 | `VOID_MATCH_SCORING` | 409 `match_awaiting_court` | 同上（探针 R3-AFTER-RET） |
| 结束待提交 | `CORRECT_SCORE_STATE` | 特殊结果待提交时引擎拒绝；若是逐分打完的比赛则 `assertCanReoccupyCourt` 拒为 `match_awaiting_court` | 带标记的比赛只可能经特殊结果到达结束待提交（离场只接受暂停中），所以后一分支实际走不到 |
| 已提交 / 已确认 | `REOPEN_RESULT` | 回到结束待提交，放行 | 不进入占用 |
| 任意 | 仅结果补录、裁判长判 WO、重开仅结果记录（`results-service.ts` 写 `SCHEDULED`） | 走不到 | 都要求 `version = 0` 且无事件；带标记的比赛一定开过局 |

即使今后有遗漏，CHECK 仍拒绝「带标记 + 未开打 / 就绪 / 进行中」，且现在映射成 409（探针 R3-DB 直写三种状态均为 `{status:409, code:"match_awaiting_court"}`）。

**约束有没有漏洞**：放宽后允许的三种状态都不打球：暂停中不能计分；结束待提交与已提交只能走提交、确认、重开、作废特殊结果。另外两条既有约束仍在：`matches_awaiting_court_has_no_court`（有标记就没有场地），触发器 `protect_started_match_schedule`（离场声明下改场地为空必须同时记标记）。没有发现借放宽进入「无场地打球」的路径。

**旧库迁移**：新 CHECK 是旧 CHECK 的超集（旧：只允许 `SUSPENDED`；新：允许 `SUSPENDED`、`ENDED_PENDING_SUBMISSION`、`SUBMITTED`），凡是满足旧约束的数据必然满足新约束，`ADD CONSTRAINT` 的全表校验不会失败。`DROP CONSTRAINT` 没有写 `IF EXISTS`，但上一个迁移一定已建立该约束（迁移按顺序执行），不构成风险。`ADD CONSTRAINT` 会短暂持有 `matches` 表的排他锁并扫全表，校园规模可以忽略。在 `review_test`（既有库）与 `review3_test`（全新库）上都已成功执行。

**错误映射**：`rethrowCourtOccupied` 只挂在 `submitScoringCommand` 与转场事务上；其他写 `lifecycleStatus` 的路径（`results-service.ts`）碰不到带标记的比赛（见上表），所以不需要映射。正则匹配约束名，Prisma 报错信息里带约束名（第二轮观察值可证）。

**遗留的显示小问题**：标记在比赛结束后保留，工作台标题行用 `snapshot.awaitingCourt` 判断，结束待提交 / 已提交的比赛仍显示「待分配场地」；看板与公开页按 `lifecycleStatus === "SUSPENDED"` 判断，同一场显示「场地待定」。见 RV3-03（P3）。

### 3.2 RV2-02：回到占场地前的 S-8 检查

**覆盖面**：新分支挂在 `submitScoringCommand` 里，凡是「前不占用（就绪 / 结束待提交 / 已提交）→ 后占用（进行中 / 暂停中）」的命令都检查，不按命令类型枚举，所以撤销、更正、作废特殊结果都覆盖，今后新增命令也自动覆盖。引擎层 `PAUSE_MATCH` 只接受进行中，所以「就绪 → 暂停中」走不到，提示中「本场已结束」的前提成立。开局（`AWAITING_OPENING_SETUP → IN_PROGRESS`）仍走原分支，提示仍是「本场暂不能开始」（探针 R3-TOSS）。抛币那步会与新分支各查一次（抛币后仍是就绪，新分支不触发），没有重复报错。

**与触发器一致**：触发器 `guard_court_single_occupancy` 的「新进入占用」= 新状态是进行中 / 暂停中，且旧状态不是这两种或换了场地；应用层的「前不占用 → 后占用」与之相同，占用判断都只算进行中 / 暂停中。应用层先给出带编号的 409，触发器兜底。带标记的比赛没有场地，触发器不检查，应用层放行回到暂停中，两边一致。

**探针**：

- 逐分打完（2:0）后同场地下一场开局：撤销最后一分 → 409 `court_occupied`，`busyMatchCode` 为下一场、`busyMatchStatus = IN_PROGRESS`；下一场暂停后再撤销 → 同样被拒，提示写「暂停中」；下一场退赛结束后撤销 → 接受，比赛回到进行中、仍在原场地，场地上只有一场（R3-REOCC）。
- 退赛后下一场开局：作废特殊结果 → 409 带编号；同时提交、重开都接受，不误拦（R3-REOCC-INV）。
- 并发：一场作废特殊结果（回进行中）与同场地另一场确认开局同时提交，10 轮（奇偶轮交换发起顺序）：每轮恰好一方成功、另一方 409 `court_occupied`，无 500、无同场两场（R3-RACE）。说明：10 轮都是作废那一方胜出，这是两条路径的耗时差，不是确定性交错；确定性交错已由第二轮 RV01-ISO 覆盖，本轮重跑仍通过。

**提示文字**：编号与状态准确；「请等那场结束后再撤销或更正」准确。但「或由裁判长按结果更正处理」对逐分记分的比赛没有可走的路径：裁判长能用的更正手段是「受控重开 + 完整比分更正」，而完整比分更正不能把比赛标为已结束（`corrected_match_already_won`），结果一定是进行中，同样被这条检查拦下；仅结果补录只接受未开过局的比赛。见 RV3-02（P3）。这部分是读代码判断，没有单独跑「重开后完整更正」。

**选手冲突**：回到进行中时不检查 S-4（选手是否在另一块场地比赛）。赛务口径 S-4 明文写「只在开局设置 → 进行中这一步检查」，所以不算缺陷，只记录。

### 3.3 RV2-03：执裁时间线

- 修法：`registered = firstHandover ? firstHandover.from : session.officiatingName`。交接审计的 `from` 由 `acquireScoringSession` 写入，取的是交接前会话上的姓名，所以 `from` 为空当且仅当会话开始时没有登记姓名，此时退回 `UNNAMED_SHARED`（平台共用账号）或账号姓名（具名账号），都正确。
- 探针：补名后再交接 → `未登记 · 甲（交接）· 乙（交接）`；从未补名、过期后另一设备取得控制 → `未登记 · 丙`；补名后裁判长接管、过期后原设备重新取得控制 → `未登记 · 甲（交接）· 裁判长接管 · 丁`，交接只归属第一段会话（`nextStart` 窗口正确）；正常登记姓名的会话 → `甲 · 乙（交接）`，与修复前相同。第二轮 O4-LINE（交接、换回、接管、过期重取）重跑仍通过。
- 具名账号（非共用）在逐场指派下不要求姓名；若续用时主动填了姓名，会写 `from = null` 的交接，时间线现为「账号姓名 → 所填姓名（交接）」，比修复前「整段记成所填姓名」更如实。读代码判断，未单独跑。

### RV3-01（P2）全新数据库上种子脚本失败：共用裁判取得控制时没有登记姓名

- 来源：O-4 提交 `42ec3ec`（不是 `8d1c355`）。`officiatingNameRequired` 对平台共用账号恒为真，`acquireScoringSession` 没有姓名就拒绝；`prisma/seed.ts` 的 `seedNormalResult`（第 174 行）与 `seedSpecialResult`（第 257 行）调用 `acquireScoringSession(input.refereeId, input.matchCode, randomUUID())` 不带姓名，而示例裁判就是平台共用账号。`42ec3ec` 补了 `tests/support/officiating-control.ts`，没有改种子。
- 复现：对一个**新建**的 `_test` 库运行 `pnpm exec dotenv -e <指向新库的 env> -- pnpm exec tsx scripts/prepare-test-database.ts`：迁移全部成功，种子输出「共用裁判账号请先填写本人姓名，再取得控制开始执裁。」并以退出码 1 结束。
- 为什么前两轮和开发自测没发现：`resultAlreadySeeded` 在比赛已有事件时直接返回，既有的开发库、测试库都已在 O-4 之前种好，不会再走到 `acquireScoringSession`。
- 影响：干净环境（新机器、新 CI、重建的开发库或演示库）上 `pnpm run db:seed`、`pnpm test`、`pnpm run test:e2e` 的准备步骤全部失败；种子半途退出，留下没有示例结果的库。对已部署的演示站与线上行为没有影响。阶段 9 要求从干净环境复现，会直接撞上。
- 建议：两处调用补上姓名（例如 `"示例裁判"`），并在 CI 或文档里加一次「全新 `_test` 库跑 `db:test:prepare`」的检查。`scripts/measure-replay-cost.ts:47` 同样不带姓名，一并处理。

### RV3-02（P3）「由裁判长按结果更正处理」对逐分记分的比赛走不通

- 位置：`scoring-command-service.ts:212` 的提示，以及赛务口径 S-8 的同一句。
- 现象：比赛逐分打完、场地已交给下一场时，撤销或更正被拦，提示建议「等那场结束」或「由裁判长按结果更正处理」。但逐分记分的比赛，裁判长的更正手段只有「受控重开 + 完整比分更正」，更正后比赛一定是进行中（引擎不允许把更正结果标为已结束），同样被拦；仅结果补录只接受未开局的比赛。所以第二个选项实际不存在，裁判长按提示去找会找不到。
- 影响：只是提示，不影响数据；实际唯一路径是等下一场结束（或下一场暂停后转场）。
- 建议：把提示与 S-8 那句改成可走的路径，例如「请等那场结束后再撤销或更正；急需更正时由裁判长让那场暂停并转到其他场地」，或者确认后删掉「按结果更正处理」。由开发会话与用户决定。

### RV3-03（P3）比赛结束后，工作台标题仍显示「待分配场地」

- 位置：`scoring-workbench.tsx:1187`（按 `snapshot.awaitingCourt`），对照 `schedule-rows.tsx:100` 与 `public-results/model.ts:107`（按 `lifecycleStatus === "SUSPENDED"`）。
- 现象：RV2-01 修复后，离场待续的比赛记录退赛并提交、确认后，离场标记一直保留。工作台标题行仍写「待分配场地」，而看板与公开页同一场写「场地待定」。读代码判断，未在浏览器复现。
- 影响：纯显示；结束的比赛不需要场地，「待分配场地」会让裁判误以为还要等转场。
- 建议：工作台改为 `snapshot.awaitingCourt && state.phase === "PAUSED"`（与下方横幅的条件一致），或服务端只在暂停中时返回 `awaitingCourt`。
