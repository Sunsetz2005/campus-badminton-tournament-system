# 全赛制并发仿真 · 测试报告

> 依据：`全赛制并发仿真-测试方案.md`（2026-10-23 批准，含 §13 追加要求）。本报告是 M6 的交付物，汇总 M1—M6 全部运行。
> 测试期间**没有修改业务代码、没有直接写库**；仿真自己的数据库会话强制只读，所有写入走产品接口。被测数据全部在独立库 `badminton_tournament_stress_test`。
> 分项记录：`并发仿真-M4异常注入记录.md`、`并发仿真-P02容量探测.md`、`并发仿真-M5赛务异常记录.md`；系统侧问题：`并发仿真-系统发现.md`（SF-01—SF-06）。

## 一句话结论

**数据层是可靠的**：L1—L3、本机与服务器、两种裁判模式、两种设备模式、全部注入与赛务异常下，九项独立判定（重放、期望比分、请求↔事件、团体胜负、
选手/场地不重叠、数据隔离、名次重算、强制同分、裁判不重叠）没有出现一处数据错误。
**需要处理的是可用性与赛务口径**：同时写入密集或同一出口观众很多时会有 500 与秒级延迟（SF-01 / SF-04 / SF-06），
团体名单揭晓会挡住整场赛事的排程发布（SF-05），弃权 / 退赛 / 转场等赛务没有补救路径（预计卡住与设计未定义，需组织方定口径）。

### 延迟与资源

| | 记分命令 P50 / P95 / P99 / 最长 | 5xx | 应用 CPU 中位 / P90 | 库 CPU 中位 / P90 |
|---|---|---|---|---|

B 的慢与 500 集中在每分钟开头约 18 秒：同一出口下公开查询被固定窗口限流整齐地集中放行，详见 **SF-06**。窗口其余时间记分 P50 约 150 ms、P95 约 1 秒。

按 P-02 的门槛（P99 < 1 秒、零 5xx），A、B 都不达标；但要注意 C8 档下 12 块场地的命令速率约相当于真实节奏的 96 块场地，

### §13.9 裁判轮换（B，逐场指派 · 个人手机）

- 自动建议给 12 人分配（每块场地一名「本场地」裁判），另人工改派 29 场；最多一人执裁 39 场，44 人中 12 人一场没排。
- 仿真裁判按真实节奏休息，场地等指派裁判到场累计 38682 秒；后段 12 块场地里常只有 3—4 块在打。系统不考虑休息（用户已决定不做休息间隔）。
- 个人设备重新登录 39 次（退出后 19、清 Cookie 后 20），最长 3.1 秒。登录会话峰值 73、活动控制会话峰值 17。

### R1 真实节奏对照

| | R1（真实节奏） | C8 对照（同种子） |
|---|---|---|
| 单场实际时长中位 | 44.6 分钟 | 6.8 分钟（× 8 ≈ 54 分钟） |
| 开始偏差中位 / P90 | −1.1 / 19.1 分钟 | −3.4 / 9.8 分钟 |
| `not_controller` | 0 | 1 场 2 次，被接管后打完 |

结论：两种节奏下的延误推算与租约行为一致。真实节奏暴露的唯一问题在**仿真脚本**：心跳原先只在两条命令之间检查，局间 120 秒等待会让 2 分钟租约过期
（修正前 4 场全部中途 `409 not_controller`）。真实裁判工作台的心跳是独立的 30 秒定时器（`src/components/scoring-workbench.tsx`），不受影响。
R1 与 B 同时运行，延迟数字受 B 拖累，不作结论。

## 系统发现汇总

| 编号 | 问题 | 严重度 | 证据 |
|---|---|---|---|
| SF-01 | 事务冲突 `P2034` 未重试即返回 500 | 高 | M3 |
| SF-02 | 出现延误后草稿带着既成硬冲突，任何调整都发布不了 | 中 | M3、M5、M6 |
| SF-03 | 数据库不可用时一律 500，客户端分不出可重试 | 低 | M4 |
| SF-04 | 同时写入密集时重试耗尽与 `P2028` 返回 500 | 中 | M4b、M6（B 的 16 次） |
| SF-05 | 团体名单揭晓与已发布个人比赛形成选手重叠，整个赛事无法再发布排程 | 中 | M5、M6（L3 开赛 5 分钟即 24 条） |
| SF-06 | 同一出口下公开查询按固定窗口集中放行，每分钟一次突发拖慢裁判记分并出现 500 | 中 | M6 |

处理方式均为「待定」，按约定由用户统一决定；测试期间没有修改。

## 需要组织方定口径的事项

方案 §11 的 P-03—P-12 之外，运行中新增：

1. SF-05 的处理方向（名单提交时检查个人项目时间 / 发布只校验本次改动 / 保持现状并提示）。
2. 团体积分榜「分层比较后剩两队」时何时回到相互胜负（M5 R4 的 S1 两种口径结果相反）。
3. 逐场指派的自动建议是否需要轮换均衡或连续执裁上限。
4. 同出口场景下公开查询额度是否够用、是否改为平滑放行（SF-06）。
5. 小组一场弃权即整体排除、淘汰空签位不轮空、团体退赛、取消资格追溯、转场、整场作废、取消比赛等（见 `并发仿真-系统发现.md` 两张「设计未定义」表）。

## 未覆盖与局限

- 共用账号模式下系统无法区分执裁人，裁判负荷只能在仿真内部统计。
- 浏览器真实操作（§13.3）只在本机 L1 做过，没有在 L3 上做；也没有真机。
- 观众只调用 `/api/public/*`，没有覆盖 `/public/*` 页面额度与 429 时的页面表现。
- 组合压力窗口没有叠加「三条延误链」（延误七情形在 M3 单独测过）。
- R1 真实节奏只跑了 2 小时、5 场；与 B 同时运行，延迟不可比。
- 服务器同机有其他项目，CPU 余量随它波动；仿真端与被测服务同机。
- 「未发布排程的比赛仍能开打，但没有公开时间与场地」只观察到前半句，公开页表现未核对。

## M6 期间修正的仿真脚本问题

| 问题 | 影响 | 处理 |
|---|---|---|
| 心跳只在命令之间检查 | 真实节奏下局间等待使租约过期 | 等待期间分段心跳（`waitAlive`） |
| 「场地后半段推迟」只推一块场地 | 下游比赛落到上一轮之前（`DEPENDENCY_ORDER`），被误判不符 | 下游比赛一并顺延，最多三轮；仍有推迟造成的新冲突记为设计未定义 |
| 资源采样名单含尚未创建的容器 | `docker stats` 整条无输出，A 轮前 30 分钟没有资源数据 | 只采样实际存在的压测容器 |
| 同种子同分钟启动两轮 | 赛事 slug 与产物目录重名；清理崩溃目录时误删了第一次 R1 的产物 | 错开启动；R1 以新种子重跑 |
| 会话峰值计入以往运行的会话、观众跨赛事取比赛编号（M5 发现） | 峰值失真、公开详情大量 404 | 只数本次运行创建的会话；只取本赛事场地上的比赛 |
