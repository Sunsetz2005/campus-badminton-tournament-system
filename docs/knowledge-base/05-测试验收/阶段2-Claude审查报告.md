#### S2-001 — `CORRECT_SCORE_STATE` 不校验「局胜负」和「换边/间歇义务」，可写入自相矛盾的比赛状态

- **严重程度：P2**
- **证据状态：运行复现**
- **位置**：`src/domain/rules/match-engine.ts` 的 `applyReplacement`（约 443—462 行）
- **对应要求**：提示词「分数更正必须显式校验新的发接发/左右分配、**局胜负和换边/间歇义务**，形成有原因、有修改前后快照的更正事件。不能只根据新比分猜四人次序。」
- **实测**：

  ```
  传统 21 分制（target 21 / cap 30），把比分更正为 25:3 且 phase=IN_PROGRESS
    → accepted，状态变为 25:3 / IN_PROGRESS / gamesWon {A:0,B:0}
  在该状态上继续 RALLY_WON(A)
    → accepted，比分变为 26:3
  把 gamesWon 设为 {A:7,B:0} 而 completedGames 为 []（三局两胜）
    → accepted
  ```

- **已经做到的部分**：`servingSide` / `serverPlayerId` / `receiverPlayerId` / `logicalCourts` 的对角与奇偶一致性**有**严格校验（非对角接发被拒），比分非负整数**有**校验。缺的是局胜负与义务两项。
- **影响**：阶段 2 是纯引擎，尚无入口，因此当前不产生错误成绩。但这是「更正」这条最需要防呆的路径：阶段 3 一旦把 `CORRECT_SCORE_STATE` 接到裁判长更正界面，一次误填就能产生一个**永远无法正常结束**的比赛（比分已越过封顶却仍在进行），且该状态会被写进 `MatchEvent` 成为权威历史。
- **最小修复建议**：在 `applyReplacement` 末尾复用既有的 `gameIsWon` / `winsNeeded`：若 `score` 已构成胜局而 `phase` 仍为 `IN_PROGRESS`/`OBLIGATIONS_PENDING` 则拒绝；校验 `gamesWon` 与 `completedGames` 的数量和归属一致；按新比分重算应有的 `INTERVAL`/`CHANGE_ENDS` 义务并与传入的 `pendingObligations` 比对。
- **建议回归测试**：断言「更正为已达封顶的比分但 phase 仍为进行中」被拒；断言「gamesWon 与 completedGames 不一致」被拒。

#### S2-002 — 手动更正物理端后再确认未处理的规则换边义务，端位被交换两次且无任何提示

- **严重程度：P2**
- **证据状态：运行复现**
- **位置**：`match-engine.ts` 的 `CORRECT_PHYSICAL_ENDS` 分支（约 523—537 行）
- **对应要求**：提示词「**手动更正物理端需核对是否同时完成未处理的规则换边义务。**」以及「规则换边每个触发点只执行一次」
- **实测**：

  ```
  单局 21 制，11 分触发 CHANGE_ENDS 义务，此时 {A:END_1, B:END_2}
  裁判先手动更正端位为 {A:END_2, B:END_1}（现场已经换过边）  → accepted
    换边义务仍然挂着：true            ← 未提示、未关联
  再确认该规则换边义务 CONFIRM_CHANGE_ENDS
    → 端位变成 {A:END_1, B:END_2}     ← 又换回去了
  ```

- **根因**：`CORRECT_PHYSICAL_ENDS` 的 `fulfillsObligationId` 只接受 `PHYSICAL_ENDS_REVIEW` 类型，**无法用于 `CHANGE_ENDS`**；该分支也不检查是否存在未处理的 `CHANGE_ENDS` 义务。于是「手动更正」与「确认规则换边」各自独立地交换了一次。
- **影响**：最终 `physicalEnds` 与场上实际相反，且整个过程全部 `accepted`，没有任何警告。物理端位是阶段 3 场地图与换边提示的输入，错误会一路传下去。
- **最小修复建议**：`CORRECT_PHYSICAL_ENDS` 允许 `fulfillsObligationId` 指向 `CHANGE_ENDS` 并在更正的同时消费该义务；或在存在未处理 `CHANGE_ENDS` 义务时拒绝裸的物理端更正，要求显式说明二者关系。
- **建议回归测试**：断言「有未处理换边义务时手动更正端位」要么消费该义务、要么被拒；断言两条路径组合后端位只被交换一次。

#### S2-003 — `replayMatch` 不是重放，而是回吐事件里存的快照；对应测试恒为真

- **严重程度：P2**
- **证据状态：运行复现**
- **位置**：`match-engine.ts` 的 `replayMatch`（末尾）与 `createEvent`（每个事件内嵌 `stateBefore` + `stateAfter` 两份完整状态）
- **对应要求**：提示词「状态可序列化、**可从初始状态与事件重放**」；最低测试集合第 9、10 条
- **实测**：

  ```
  真实状态 1:1
  篡改最后一个事件的 stateAfter.score 为 99:99
    → replayMatch 返回 99:99          ← 原样回吐，未从命令重算
  篡改事件快照内 ruleConfig.targetPoints 为 999
    → replayMatch 返回 999
  ```

  `replayMatch` 只校验 `version` 连续性，然后 `state = clone(event.stateAfter)`。
- **连带问题**：测试「事件重放和 JSON 往返得到相同权威状态」断言的是
  `replayMatch(serialized.initialState, serialized.events) === serialized.state`，
  而 `aggregate.state` 本身就是最后一个事件的 `stateAfter` 的副本。**该断言在任何实现下都成立**，包括引擎逻辑被改坏的情况。因此提示词第 9、10 条的「确定性重放」实际没有被验证。
- **影响**：阶段 2 内部自洽，不产生错误结果。但 `CLAUDE.md` 与 `AGENTS.md` 把 `MatchEvent.commandId @unique` + `@@unique([matchId, version])` 明确定位为「幂等与**确定性重放**」的基础，阶段 3 要靠重放做崩溃恢复与争议追溯。如果重放等于「相信存下来的快照」，那么快照一旦写错或引擎升级后语义变化，就没有任何机制能发现。
- **次要影响**：实测每事件约 2.0 KB（内嵌两份完整状态），一局 21 分 24 个事件约 50 KB，三局两胜约 90 回合推算 ≈ 0.18 MB/场。单场可接受，但作为 `MatchEvent` 表的行载荷偏重，且使事件日志出现「命令」与「快照」两个事实来源。
- **最小修复建议**：`replayMatch` 改为从 `initialState` 逐条**重新执行命令**（事件已保存 `type` + `payload`），再与存下的 `stateAfter` 比对，不一致时抛错；或至少提供一个 `verifyReplay` 做该比对。事件可只保留命令与轻量差异，`stateAfter` 作为校验用摘要（如状态哈希）而非权威副本。
- **建议回归测试**：一条「篡改事件快照后重放必须抛错」的用例——这条用例在当前实现下会失败，正好证明它有效。

#### S2-004 — 连续误点只能撤销一次，且该限制比文档写的更严

- **严重程度：P3**
- **证据状态：运行复现**
- **位置**：`match-engine.ts` 的 `applyUndo`（`undo_has_later_operations` 判定）
- **实测**：

  ```
  连点两次 RALLY_WON(A) → 2:0（假设两次都点错）
  第 1 次 UNDO → accepted，回到 1:0
  第 2 次 UNDO → rejected (undo_has_later_operations)
                 「目标得分之后已有独立操作，不能普通撤销。」
  ```

  被撤销的第 2 分虽已作废，但它的事件仍留在 `later` 集合里，且 `RALLY_WON` 不在允许跟随的 `dependentTypes` 中，于是**从未被撤销过**的第 1 分也无法再撤销。
- **文档口径不一致**：`03-竞赛规则/换边撤销与更正.md` 本轮新增的表述是「已经被撤销的命令不能再次普通撤销，撤销事件本身不能反撤销」——这描述的是**另一条**限制。实际行为额外禁止了「撤销上一个未被撤销的得分」，文档未写。
- **影响**：裁判在快速回合中连续误点两次是常见场景，目前第二次只能走更重的更正流程。提示词要求「撤销最近可逆误操作」，也要求「后面已有独立比赛操作时不能无条件倒回」——已被撤销的得分是否算「独立操作」，是一个需要明确的产品决定，而不是让实现口径与文档口径分叉。
- **最小修复建议**：在 `later` 判定中排除已被 `alreadyUndone` 标记的 `RALLY_WON` 事件；若确实选择保留当前限制，则把「撤销后不能继续向前撤销」明确写进文档与裁判手册。

### 七、阶段 2 验收判定

| 提示词要求 | 证据 | 判定 |
|---|---|---|
| 纯函数 `applyCommand(state, command) -> result`，输入失败不产生半更新 | 非法命令/负分/非对角均 `rejected` 且原聚合逐字节不变 | **通过** |
| 时间与随机从外部事件传入 | 引擎无 `Date.now()`/`Math.random()`；抛币事实由命令载荷提供 | **通过** |
| 状态可序列化 | JSON 往返正常 | **通过** |
| 可从初始状态与事件重放 | 实现为回吐快照，非重算 | **不通过 — S2-003** |
| 状态链与合法转换 | 11 个 phase，转换点均有断言（局末、赛末、暂停、提交、确认、重开、特殊结果） | **通过** |
| 固定保存 A/B、成员、物理端、R/L、发接发、局号、局分、胜局、规则快照、待确认、版本 | `MatchState` 字段齐全，A/B 与物理端、逻辑 R/L、屏幕方向严格分离（无屏幕字段） | **通过** |
| 必须实现的规则命令（抛币、开局、RallyWon、Let、换边三类、R/L 更正、发接发更正、分数更正、撤销、局间、暂停、提交、重开、特殊结果） | 20 个命令类型全部存在且为**独立命令** | **通过** |
| 双打自动分配要求 | 黄金轨迹 8/8 逐格命中，含两条难点 | **通过** |
| 更正与换边的详细边界 | 分数更正缺局胜负/义务校验；手动端位更正未核对换边义务 | **部分不通过 — S2-001、S2-002** |
| 10 项最低测试集合 | 第 1—8 项独立取证通过；第 9、10 项因 S2-003 未被真正验证 | **8/10 通过** |
| 用规则→测试名→结果表记录证据 | `05-测试验收/测试记录.md` 已有该表，并声明「不是 Claude 独立复验结论」 | **通过** |
| 列出尚待老师确认的规则问题 | 未更新 | **不通过 — S2-005** |
| 纯引擎通过后停止 | 无新迁移、无新 API、无 UI | **通过** |

**总评：阶段 2 主体通过，但不能判为完整通过。**

理由：

1. **计分与双打发接发这一最核心、最容易错的部分是正确的。** 我用独立脚本逐格复算了提示词的黄金轨迹，8 行全中，两条难点（发球方连得换区不换人、接发方得分不无条件换人）都对；单打奇偶、20:20/22:20、29:29/30:29、3×15 的 14:14/21:20、义务只触发一次、局末拒绝加分，全部独立复现通过。
2. **3 个问题落在提示词明确写出的要求上**：S2-001 与 S2-002 是「更正与换边的详细边界」里逐字列出的两条；S2-003 使第 9、10 项测试失去效力。
3. 这些都不是「算错分」，而是**更正与恢复路径的防呆缺口**——恰恰是阶段 3 接上持久化、租约和接管后最难补救的部分。

**是否可以进入阶段 3：建议先修 S2-001、S2-002、S2-003 再进入。**

不是因为阶段 2 不可用，而是因为这三条正好卡在阶段 3 的地基上：阶段 3 要把事件写进 `MatchEvent` 表并依赖重放做恢复与追溯（S2-003），要把更正命令接到裁判长界面（S2-001、S2-002）。在纯引擎里修是改几十行；等写入数据库并产生真实历史后再修，就要处理已落库的错误状态。

S2-004—S2-006 可以与阶段 3 并行处理，不构成前置条件。

阶段 1 遗留的 S1-010—S1-014 **五项全部复验通过**，不再是阶段 3 的前置条件。
