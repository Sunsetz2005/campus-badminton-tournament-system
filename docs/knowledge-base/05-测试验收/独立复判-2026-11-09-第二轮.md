### 3.1 RV-01（S-8）细节

**机制核对**（`prisma/migrations/20261109120000_court_occupancy_guard/migration.sql`）：

- 触发器 `matches_court_single_occupancy` 是 `BEFORE INSERT OR UPDATE OF "courtId", "lifecycleStatus"`，只在「新进入占用」（变为 IN_PROGRESS/SUSPENDED，或换到另一块场地）时执行；先 `UPDATE "courts" SET "sortOrder" = "sortOrder"` 取得场地行锁，再查同场地其他占用比赛。
- 读已提交：后到的事务在场地行锁上排队；PL/pgSQL 里每条语句重新取快照，所以拿到锁后的 `SELECT` 能看到对方已提交的比赛 → `court_occupied`。
- 可串行化：改写一行已被并发事务改写并提交的行 → `40001`，`runTransaction`（`transaction-retry.ts` 把 P2034/40001 视为可重试）整体重跑，重跑时应用层 `court_busy` / `court_occupied` 给出带编号的提示。

**探针 RV01-ISO（确定性，不靠碰运气）**：第二个事务先执行一条读取（可串行化下快照在此确定），第一个事务改写比赛并持锁，用 `pg_blocking_pids` 确认第二个事务已被场地行锁挡住，再放行第一个提交。四种组合（RC→RC、RC→SER、SER→RC、SER→SER）后者全部被拒，场地上始终只有一场。这直接覆盖了第一轮报告担心的「读已提交与可串行化混用」，也覆盖了今后如果有人新增一条读已提交的写入路径。

**写入路径排查**（哪些写入能让比赛「进入占用」）：

| 路径 | 是否进入占用 | 应用层检查 | 数据库兜底 |
|---|---|---|---|
| 开局 `CONFIRM_OPENING_SETUP`（READY→IN_PROGRESS） | 是 | `assertCourtFree` + `assertPlayersNotOnCourt`，可串行化 | 触发器 |
| 转场 `transferSuspendedMatch` | 是（换场地） | `court_busy`，现为可串行化 | 触发器 |
| `RESUME_MATCH`、暂停 | 否（已在占用中） | 离场待续时 `assertHasCourtToResume` | — |
| 裁判长接管 `takeoverScoringSession` | 否（不改状态和场地） | — | — |
| `REOPEN_RESULT` | 否（回到 `submittedFromPhase`，即结束待提交） | — | — |
| `UNDO_LAST_REVERSIBLE` / `CORRECT_SCORE_STATE` 让结束待提交回到进行中 | **是** | **无**（只在抛币/开局两步检查） | 触发器拒绝，提示文字不准确，见 RV2-02 |
| 作废计分后重新开局 | 是 | 同开局 | 触发器 |
| 仅结果补录、裁判长判 WO（`results-service.ts`） | 否（只写 SUBMITTED，且要求未开始） | — | — |
| 发布赛程、草稿编辑、团体小场生成 | 否（只写 SCHEDULED/READY 的场地） | — | — |
| 种子 | 全部 `upsert`；更新时值不变不触发，新建时若同场两场进行中会被拒 | — | 触发器 |

结论：应用层把比赛放进占用的写入，现在都在可串行化事务里；即使今后有遗漏，触发器也在两种隔离级别下兜住。

**死锁与性能**：

- 锁顺序：开局/转场都是「比赛行（`FOR UPDATE`）→ 场地行（触发器）」；转场前还有赛事行。`updateCourt` 是「赛事行 → 场地行」，之后只做 `count`，不锁比赛行。没有找到「先场地后比赛」的路径，不构成环。
- 外键：`matches.courtId` 的外键检查取 `FOR KEY SHARE`，触发器的「原值更新」不改键列，取的是 `FOR NO KEY UPDATE`，两者兼容，不会因此互等。
- 开销：每场比赛只在开局（以及转场）时多一次单行 UPDATE + 一次走 `matches_courtId_scheduledAt_idx` 前缀的查询；场地行锁只让**同一块场地**上的并发开局排队，不同场地互不影响。可串行化下同场并发开局会有一次 40001 重试，属预期。没有做压测，只是读代码判断。

**「不追溯旧数据」是否合理**：合理。触发器只拦「新进入」，S-8 上线前已经同场多场的比赛照常可续打、结束（开发用例 `RV-01 数据库兜底` 断言了暂停 ↔ 进行中不受影响）；第三场想进入同一块场地仍会被拒。代价是数据库层面不能表述成「任何时刻至多一场」，只能表述成「不会新增」。没有发现借此绕过的写入路径。建议在演示库上做一次只读核对（见 §6），确认旧数据里实际有没有同场多场，有的话由裁判长处理掉，以后的「至多一场」就成立了。

### 3.2 RV-02（S-9）细节

- 已修好的：离场待续时 `VOID_MATCH_SCORING` 与开局都被 `match_awaiting_court` 拒绝（开发用例断言了 409 与 code）；CHECK `matches_awaiting_court_only_suspended` 生效（开发用例直接写 READY 被拒）；离场声明下只改场地、不记标记被触发器拒绝（开发用例断言）；转场后作废照常（开发用例断言）。
- 本轮排查离开「暂停中」的其他命令：
  - `RESUME_MATCH`：`assertHasCourtToResume` 拦住。
  - `CORRECT_SCORE_STATE`：引擎不允许在 PAUSED 更正（`assertScoreCorrectionAllowed`），探针确认被拒、状态不变。
  - `UNDO_LAST_REVERSIBLE`：最后一个可撤销事件之后有 `PAUSE_MATCH`（非附属事件），引擎拒绝。
  - `REOPEN_RESULT`、`CONFIRM_RESULT`：PAUSED 下引擎拒绝。
  - 仅结果补录、裁判长判 WO：只针对未开始的比赛。
  - **`RECORD_SPECIAL_OUTCOME`（退赛 RET、弃权 WO、取消资格 DSQ、中止 ABANDONED）**：PAUSED 是可记录相位（`special-outcome.ts` 的 `RECORDABLE_PHASES`），引擎接受，比赛投影为「结束待提交」，但 `awaitingCourtSince` 没有清除 → CHECK 违反 → Prisma 原样抛出（P2039 / SQLSTATE 23514），`errorResponse` 回答 **500 `internal_error`「服务暂时不可用」**。数据回滚，比赛仍是离场待续（探针 RV02-RET）。见 RV2-01。
- 结论：RV-02 原问题（无场地开打）已关闭，数据库不会出现「无场地却进行中」；但新的 CHECK 把一个合法操作变成了 500。

### 3.3 方案 B2 / O-4 细节

**取得控制的入口**：

- 唯一取得「裁判」控制会话的服务函数是 `acquireScoringSession`，`POST /api/matches/[matchCode]/control` 直接把请求体的 `officiatingName` 交给它；姓名校验在服务端（`officiatingNameRequired(refereeMode, platformReferee)`），不依赖页面。
- 同一设备续用（`resumed` 分支）同样先过姓名校验：探针确认续用不带姓名、或只有空格，都回答 400 `officiating_name_required`。
- 同一共用账号换一台设备：`controller_exists`，不能借此改名。
- 心跳续租不要求姓名，只延长既有会话；裁判长接管走 `takeoverScoringSession`，要求 `CHIEF_REFEREE`，而 `chief-referee-service.ts` 拒绝把平台共用账号授予裁判长（`platform_referee_not_allowed`），所以接管入口不会出现「共用账号不填姓名」。
- API 表单允许 80 字，服务端 `normalizeOfficiatingName` 折叠空白并截到 40 字；页面输入框 `maxLength=40`。

**时间线还原**（探针 O4-LINE）：同一设备「甲 → 乙 → 乙（重复，不记）→ 甲（换回）」，裁判长接管，裁判长会话过期后另一台设备「丙」取得控制，再过期后同设备「丁」重新取得控制，还原结果是
`甲 · 乙（交接）· 甲（交接）· 裁判长接管 · 丙 · 丁`，与实际顺序一致；最初登记的姓名确实从第一条交接审计的 `from` 找回。会话过期后重新取得控制记为一次新的「取得控制」而不是「交接」，这与「交接 = 同一会话换人」的定义一致，可接受。

**公开边界**：

- 静态：`public-tournament-service.ts`、`public-projection.ts`、`report-snapshot-service.ts`、`src/reports/*`、`src/app/api/public/**` 都不查询 `scoringSession`、`officialAssignment`、`auditLog`，也不引用 `officiating-record.ts`。`ScheduleRows`（含执裁记录一行）只被 `/management/[slug]/schedule` 与 `/officiating/board/[slug]` 使用。
- 动态（探针 O4-LEAK）：赛事设为已发布、全部比赛设为已发布，以唯一姓名取得控制后，公开赛事、公开赛程、公开比赛详情、对外快照（成绩册与 PDF 共用的数据源）、对外数据表 .xlsx 解压后的全部 XML 都**不含**该姓名；对照组内部名单 .xlsx **含**该姓名，证明搜索方法有效。PDF 本身没有渲染（需要无头 Chromium），依据是它与数据表共用同一份快照。
- 内部名单：生成用 `rolesFor("REGISTRATIONS_INTERNAL") = ADMIN/ORGANIZER`，下载 `getReportExportFile` 再按 `canDownload` 复核同一组角色；裁判长能看看板与复核卡片上的执裁记录，但不能生成或下载内部名单。与改动前一致。

**开发用例核对**：`match-day-rules.test.ts` 的 B2 用例真实断言了「逐场指派下共用账号必填、具名账号不必填、交接与接管顺序、看板/复核/内部名单三处显示、对外数据表不含两个姓名」；没有覆盖续用不带姓名、换回同名、过期重取与旧会话，本轮探针补上。

### RV2-01（P2）离场待续的比赛记录退赛/弃权等特殊结果时回答 500

- 复现：比赛开局 → `PAUSE_MATCH` → 裁判长 `releaseSuspendedMatchCourt`（离场待续）→ 主裁判（或接管后的裁判长）提交 `RECORD_SPECIAL_OUTCOME { type: "RET", winnerSide: "A" }`。探针 `tests/review/round2-review.probe.ts`「主裁判在离场待续时记录退赛」。
- 现象：`updateProjections`（`src/server/services/scoring-command-service.ts:246`）把 `lifecycleStatus` 写成 `ENDED_PENDING_SUBMISSION`，`awaitingCourtSince` 仍有值，违反 `matches_awaiting_court_only_suspended`（迁移 `20261109120000_court_occupancy_guard`）；错误不是 `AppError`，`errorResponse` 回答 500「服务暂时不可用，请稍后重试」，工作台会让裁判重试，重试仍失败。数据完整回滚，没有坏数据。
- 影响：S-9 的典型用法就是「伤停离场待医疗处理」，随后最常见的结局是退赛。场地全满时（也就是用离场的原因）只能干等一块空场地，先转场再记退赛；提示文字不能告诉裁判该怎么办。
- 建议修法（二选一，由开发会话决定）：
  1. 推荐：把 CHECK 放宽为「离场待续的比赛不能处于会打球的状态」，例如 `"awaitingCourtSince" IS NULL OR "lifecycleStatus" IN ('SUSPENDED', 'ENDED_PENDING_SUBMISSION', 'SUBMITTED')`，记录特殊结果时保留标记。这样 `INVALIDATE_SPECIAL_OUTCOME` 回到暂停中时标记仍在，仍须先转场才能恢复；若改成「记录特殊结果时清除标记」，作废特殊结果后比赛会变成「暂停中、无场地、无标记」，`assertHasCourtToResume` 只看标记，会重新打开 RV-02 的口子。
  2. 至少：在 `submitScoringCommand` 里离场待续时把这类命令拒为 409（明确提示「先转场」），不要落到 500。
  - 无论哪种，都补一条集成用例：离场待续 → 记录退赛 → 提交 → 复核；以及离场待续 → 记录退赛 → 作废特殊结果 → 恢复仍被 `match_awaiting_court` 拒绝。

### RV2-02（P3）结束后场地已被下一场占用，再撤销最后一分得到不准确的 409

- 复现：比赛 m 在场地 1 打到「结束待提交」，同场地比赛 n 开局，m 的裁判提交 `UNDO_LAST_REVERSIBLE`。探针「撤销让结束待提交的比赛回到进行中」。
- 现象：触发器拒绝（行为本身符合 S-8：比赛回到进行中需要场地），`rethrowCourtOccupied` 回答 409「这块场地**刚**被另一场比赛占用……」；实际上场地已被占用了一段时间，提示也没写占用的比赛编号。应用层的 `assertCourtFree` 只在抛币与开局两步调用，这条路径没有带编号的友好提示。`CORRECT_SCORE_STATE` 把结束待提交改回进行中是同一路径（读代码判断，未单独跑）。
- 影响：裁判长没有可走的路径——转场只接受暂停中，比赛此时是结束待提交；只能等下一场结束，或改走结果更正。
- 建议：在 `submitScoringCommand` 里，凡是前后相位从「不占用」变成 IN_PROGRESS/PAUSED 的命令都调用 `assertCourtFree`（复用带编号的提示）；在决定文件里写明「比赛结束后场地已被占用时，撤销/更正应在下一场结束后进行，或由裁判长按结果更正处理」。

### RV2-03（P3）B2 上线前建立的未登记姓名会话，续用补填姓名后被记成「从头就是这个人」

- 复现：逐场指派模式下共用账号建立的控制会话 `officiatingName = null`（B2 上线前的旧会话；探针直接把会话姓名置空来模拟），同一设备再以「后来的人」续用。探针「未登记姓名的旧会话」。
- 现象：续用写了交接审计 `{ from: null, to: "后来的人" }`；`loadOfficiatingRecords`（`src/server/services/officiating-record.ts:95`）取 `firstHandover?.from ?? session.officiatingName`，`from` 为 null 时退回到**已被原地改写**的会话姓名「后来的人」，接着把同名的交接去重掉，时间线只剩 `后来的人`（从会话开始时刻算起），丢了「共用账号（未登记姓名）」那一段。
- 影响：只影响 B2 部署时正在进行、且之后续用的比赛（以及今后若在赛中切换裁判模式）。演示站 2026-11-09 已部署，范围很小。
- 建议：交接审计里 `from` 为 null 时，把会话起点记为 `UNNAMED_SHARED`（或具名账号姓名），即用 `firstHandover ? (firstHandover.from ?? 未登记) : session.officiatingName`。

### RV2-04（P3，提示）共用设备上姓名输入框预填上一位裁判的姓名

- `scoring-workbench.tsx` 把姓名记在 `localStorage`（`badminton-officiating-name`），下一位裁判在同一台设备上新开页面时输入框已填好上一位的姓名，不改就会以上一位的名义取得控制。决定文件已写明「姓名是自由文本，只保证事后可追溯」，所以不算缺陷；建议输入框旁加一句「不是你本人请改成你的姓名」，或预填时选中文字。未改动、未在浏览器复现。
