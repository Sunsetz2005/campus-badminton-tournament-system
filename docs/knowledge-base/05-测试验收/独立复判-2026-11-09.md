## 4. 问题清单

没有发现 P0、P1。

### RV-01（P2）转场与开局并发时，一块场地上会同时有两场

- **现象**：裁判长把暂停中的比赛 M 转到场地 C2，与此同时 C2 上已抛币的比赛 N 确认开局。两个请求都成功，C2 上同时出现 M（暂停中）和 N（进行中）。
- **复现**：`tests/review/court-race-review.probe.ts`「20 轮并发」：三次运行分别为 `doubled 20`、`doubled 20`、`doubled 19`（唯一一轮被拒的结果是 `court_occupied`）。同文件的顺序对照（先开局再转场 → `court_busy`；先转场再开局 → `court_occupied`）通过，说明判断逻辑没错，问题出在并发上。
- **原因**：`transferSuspendedMatch`（`src/server/services/schedule-service.ts:812-878`）用默认隔离级别（读已提交），只锁赛事行和被转比赛行；开局命令（`src/server/services/scoring-command-service.ts:362-401`）是可串行化事务，但不锁赛事行，也不锁目标场地。PostgreSQL 的可串行化冲突检测只在可串行化事务之间生效，所以两边都读到「C2 空闲」后各自提交。
- **影响**：违反 S-8「一块场地一场」；赛务口径文件里「可串行化事务兜底并发」的说法对这一对操作不成立。
- **建议**：在数据库加兜底，例如 `matches("courtId") WHERE "lifecycleStatus" IN ('IN_PROGRESS','SUSPENDED')` 上的部分唯一索引；或者两条路径都先 `SELECT … FROM courts WHERE id = … FOR UPDATE` 再判断占用。修复后补一个与本探针等价的确定性并发测试（可用 `tests/support/db-barrier.ts`）。

### RV-02（P2）离场待续后作废计分（S-7），比赛无场地重新开打，且再也分配不了场地

- **复现**：`tests/review/match-day-review.probe.ts`「RV-S9-B」（用例通过即确认缺陷存在）：开局 → 裁判长接管 → 暂停 → 离场待续 → `VOID_MATCH_SCORING` → 比赛变为 `READY`、`courtId = null`、`awaitingCourtSince` 仍有值 → `transferSuspendedMatch` 被拒（`match_not_suspended`）→ 重新抛币、确认开局都成功 → `IN_PROGRESS` 且没有场地。
- **原因**：`VOIDABLE_PHASES` 包含 `PAUSED`（`src/domain/rules/match-engine.ts:1091`）；`assertHasCourtToResume` 只拦 `RESUME_MATCH`（`scoring-command-service.ts:390`）；`assertCourtFree` 遇到无场地直接放行（`:196-197`）；`version > 0` 后触发器冻结场地，S-5 又只接受暂停中的比赛。
- **影响**：这场比赛会在「待分配场地」状态下进行，现场看板、公开页和 S-8 都管不到它；工作台标题一直显示「待分配场地」（`scoring-workbench.tsx:1184` 不看相位）。
- **建议**：`awaitingCourtSince` 非空时拒绝 `VOID_MATCH_SCORING`（提示先转场再作废），或者作废命令同时要求有场地；另外在开局两处检查里把「`awaitingCourtSince` 非空」当作不能开始。相关的小缺口：CHECK 只约束「离场待续 ⇒ 无场地」，探针 RV-S9-A 显示在离场声明下把场地改为空时可以不写 `awaitingCourtSince`，可一并考虑。

### RV-03（P2，测试质量，**不是产品缺陷**）`schedule.test.ts` 写死的比赛日已过期，`pnpm test` 从 2026-11 起持续红

- **现象**：12 项失败，`placed` 都是 0。用例写死 2026-11-02/03 为比赛日，`suggestDraft` 把 `notBefore` 取 `max(输入, now)`（`schedule-service.ts:463,475`），今天（2026-11-09）之后就没有可排的时段了。
- **证据**：同一文件在时钟平移探针下 21/21 通过（`tests/review/vitest.review-clock.config.ts`）。
- **影响**：门禁命令 `pnpm test` 不能再作为通过证据；之后任何人跑全量都会遇到 12 项红灯，真正的回归可能被掩盖。
- **定性**：产品代码在这一点上没有变化，自动建议只排「现在之后」的时段是预期行为；这是测试本身的问题。开发会话 2026-11-09 告知会在下一个提交里把日期改成按运行时间推算，复判人不修。
- **建议**：比赛日改成相对「今天」的日期，或者给服务层注入时钟。其余测试文件里只有极少量晚于今天的日期，而且不依赖当前时间。

### RV-04（P3）e2e 在本机负载高时有超时抖动

- 全量 e2e 中 `shared-referee.spec.ts:60` 与 `team-draw.spec.ts:78` 都停在「处理中…/正在验证…」直到超时（负载 6.4，dev 服务器打印过 `The destination stream closed early`）；单独重跑 7/7 通过。
- 隔离情况：本轮测试用独立库 `badminton_tournament_review_test`，夹具不会被另一边改动；3100 端口开跑前确认空闲，e2e 服务器正常启动。但开发会话可能同时在本机跑测试，这会抬高负载。复判人无法确认当时另一边是否在跑，所以不排除这两项超时与另一边的负载有关。
- 建议：给登录与开通账号这类口令哈希步骤放宽断言超时，或者让 e2e 跑在生产构建上。

### RV-05（P3）已抛币未开局的比赛永远换不了场地

- 抛币后 `version > 0`，触发器冻结场地；S-5 只接受暂停中的比赛。S-8 只把进行中/暂停中算作占用，所以同一场地上两场都可以先抛币，第二场会被锁在这块场地上，直到第一场结束。如果这块场地随后关闭，这场比赛无处可去：抛币和开局检查都不看 `court.active`，探针 RV-S9-A 第二条用例确认两种声明都放不开它。
- 建议：明确这是不是预期口径；需要的话，给「已抛币未开局」开一个与转场同构的例外，或者在开局时拒绝已关闭的场地。

### RV-06（P3，测试质量）S-8「占用判定」用例对已结束状态是同义反复

- `tests/integration/match-day-rules.test.ts:224-230` 对 `ENDED_PENDING_SUBMISSION`/`SUBMITTED` 是把产品查询在测试里重写了一遍再计数，没有调用产品函数；`SUBMITTED` 这条始终没有走过产品路径。

### RV-07（P3）报表存档只防改写，不防删除
