# 裁判端交互规范

主裁判端是 V1 的高风险核心。界面必须反映服务器权威状态，不能做“按钮看似成功、后台未保存”的演示壳。

阶段 3 已在 `/officiating/[matchCode]` 实现服务端鉴权和初始数据、最小客户端工作台、权威轮询/心跳、响应未知对账、无乐观比分、独立更正入口及裁判长复核。

2026-09-20 完成场地化改造：横向 SVG 模拟场地（按 Diagram A 画线）、`左侧换位 — 换边 — 右侧换位` 三按钮、独立大比分行、`左方+1 / 更正−1 ‖ 更正−1 / 右方+1` 操作行、长姓名不再截断、次要操作收进折叠抽屉。本轮 lint/typecheck/build 通过，`pnpm test` 114/114、Playwright 43/43、生产启动安全 4/4、同步脚本 10/10，并留存 before/after 各 13 张同尺寸截图。详见 [场地化裁判工作台](场地化裁判工作台.md) 与 [裁判工作台改造-审查与验收](../05-测试验收/裁判工作台改造-审查与验收.md)。

既有手机竖屏与平板横屏证据仅为 Chromium 浏览器设备模拟，真机与现场人工操作未测试；改造结果尚待用户确认与独立复验。

## 比赛生命周期

```text
SCHEDULED
  → READY_FOR_COIN_TOSS
  → READY_FOR_OPENING_SETUP
  → IN_PROGRESS
  ↔ PAUSED / INTERVAL
  → PENDING_RESULT_CONFIRMATION
  → CONFIRMED
```

弃权、退赛、取消或中止使用受权限控制的特殊分支。`CONFIRMED` 后普通主裁判不能回到 `IN_PROGRESS`。接管状态和联网状态是正交维度，不应被硬塞成比赛生命周期。

## 页面阅读顺序

工作台按“紧凑状态栏 → 完整球场 → 左侧换位/换边/右侧换位 → 大比分 → 双方加分与更正 → 精简状态 → 折叠的次要操作与历史”排列。平板横屏首屏应容纳状态栏、完整球场和主比分操作；手机竖屏仍保留横向球场，不把 A/B 大比分卡纵向堆成长页面。

| 区域 | 必须展示/操作 |
|---|---|
| 紧凑状态栏 | 比赛编号、场地、当前局、网络、控制权、命令同步、服务器版本和只读原因 |
| 完整球场 | A/B 固定身份、四个规则发球区、单双打球员、物理场地端、发球/接发身份 |
| 场地操作 | 双打左右换位更正、单打站位核对、确认换边/端位更正、本机视角翻转 |
| 大比分 | 双方名称与等宽数字比分，跟随画面左右队伍，绑定稳定 sideId |
| 比分操作 | `左方+1 / 更正−1 ‖ 更正−1 / 右方+1`，已完成局比分 |
| 折叠次要区 | 暂停、详细更正、异常结果、接管、视角、事件记录；待提交或复核时默认展开 |
| 辅助操作 | 间歇、暂停、LET、特殊结果和其他受权限控制的更正 |
| 历史与提交 | 命令状态、操作历史、前后对比、结束提交、结果复核/锁定 |

## 球场投影契约

场地图只调用纯投影 `buildCourtViewModel(state, flipped)`，不得在 React 组件中复制计分、换位或发接发算法。投影输入只来自服务器权威状态中的 `logicalCourts`、`physicalEnds`、`serverPlayerId`、`receiverPlayerId` 及本机 `flipped` 偏好。

- 正常视角左侧为 `END_1`、右侧为 `END_2`；翻转后整体旋转 180°，左侧变为 `END_2`、右侧变为 `END_1`。
- 屏幕左半场上格为 L、下格为 R；右半场上格为 R、下格为 L。同名发球区因此在画面上斜对角相对。
- `physicalEnds` 决定 A/B 当前占据哪一半场。确认换边后队伍、球员和该队比分面板整体移动；比分值仍绑定 `score.A` / `score.B`，绝不因屏幕位置交换归属。
- 双打四名球员各占一个规则发球区；单打每方只占下一球对应的一个发球区，另一格明确显示为空。
- 只有 `IN_PROGRESS`、`OBLIGATIONS_PENDING`、`PAUSED` 显示当前“发球 / 接发”；赛前设置显示“拟首发 / 拟首接”，局间未确认和比赛结束不误标当前发球员。
- 发球身份使用可缩放、可着色、可访问文本伴随的内联 SVG 羽毛球标记，不用状态关键的位图，也不只靠颜色表达。

球场标题必须明确“四格表示下一次发球前的规则位置”，不能让用户误以为系统追踪回合中的实时跑位。

## 开赛前

1. 裁判只看到本人获授权比赛；取得写租约后才能进入可操作状态。
2. 抛硬币支持记录现场结果或软件随机辅助。胜方可以选择先发球、先接发球，或选择场地；失利方选择剩余维度。界面不能把胜方限制为“先发球或场地”。
3. 已保存的抽签不能通过刷新重抽。重新抽签需要权限、原因和追加历史。
4. 每局开局确认首发方、首发球员、斜对角首接球员和双方物理端；双打允许选择非名单第一人的首发/首接，再生成双方合法 R/L。
5. 未确认前场地图只显示设置草稿，并用“拟首发 / 拟首接”标识；确认成功后才切换为服务器权威状态。

无明确有效结果时可记录无效后重做。结果已确认后，刷新、重连或不满意都不能重抽；第一球前确需作废由裁判长批准，第一球后不提供普通重抽。后续局不重抛，上一局胜方先发，双打重新确认首发/首接。

## 设备提交状态

```text
SYNCED
  → SUBMITTING(commandId)
  → CONFIRMED
  ↘ UNKNOWN → RECONCILING → CONFIRMED / CONFLICT

OFFLINE_READ_ONLY
STALE_VERSION_READ_ONLY
NOT_CONTROLLER_READ_ONLY
```

- 只有 `CONFIRMED` 才把操作显示为服务器成功。
- `UNKNOWN` 保存完整待确认命令并保留原命令 ID，阻止重复点击造成新命令；刷新或恢复网络后先查询原 ID，查不到时也只能用同一命令重试。
- `CONFLICT`、失去租约或断网时先切只读，再拉取权威状态。
- V1 不允许离线继续记分，恢复连接后先同步再开放按钮。
- 网络、控制权和命令同步是三种独立文字状态，不能只用一个彩色圆点代替。

## 得分、撤销和更正

点击 `+1` 只在 `click` 提交一次 `RALLY_WON`；按下反馈可以立即显示，但服务器响应前比分、站位和羽毛球标记均保持最后确认值。所有写按钮共享单一在途锁。

`−` 不是减分命令，只打开撤销预览。服务端预览必须证明最近一分属于被点击方，再允许填写原因并确认；取消预览不写事件，核对失败则引导使用完整比分更正。

双打每方提供“更正本方换位”，交换该方 R/L 后先走服务端预览并要求原因。单打提供“核对站位”，引导裁判更正比分或发球方，不创建任意左右换位。中央场地按钮按状态工作：

- 有 `CHANGE_ENDS` 待办时，默认“确认已换边”；若现场端位记录本身有误，则明确选择 `FULFILL` 或 `KEEP_PENDING` 后预览。
- 无换边待办时为“更正场地端”，要求原因和预览。
- 本机“翻转视角”独立保存，不产生命令、事件或版本变化。

工作台内所有原因输入和危险确认使用统一受控抽屉/对话框，不调用浏览器原生 `prompt/confirm`，也不依赖拖拽。抽屉支持初始焦点、Escape 关闭、键盘确认、字段级错误和返回原路径；核心功能必须有普通按钮和键盘路径。

## 结果确认

提交前展示每局比分、特殊结果、双方身份和未解决的待确认命令。主裁判提交后进入待复核并失去普通编辑权；裁判长可以退回补正或复核锁定。只有锁定结果进入正式排名、晋级和成绩册。锁定后更正生成新版本并跳转影响预览，不在比分页静默改值。

## 阶段 3 实现证据

- 当前实现已经加入完整球场投影、内联 SVG 发球标记、拟首发/拟首接草稿、双打换位/单打核对、场地端关系选择及 `−` 撤销预览；本轮完整自动化门禁和独立复验尚未完成。
- 核心触控目标至少 48 CSS px，比分按钮至少 56 CSS px；按下有即时视觉反馈，但只在 `click` 提交一次。
- 顶部状态区分别展示服务器版本、网络、控制权和命令同步；离线、响应未知、冲突或失去控制时切为只读，球场保持最后确认状态。
- 姓名、队伍、A/B、R/L 和发接发身份都有文字表达，不依赖颜色；200% 字体下不得遮挡核心操作。
- 位置变化采用静态切换或短淡入，只使用 `transform` / `opacity`，不增加动画库；实现 `prefers-reduced-motion`、`prefers-reduced-transparency`、`prefers-contrast`。
- 间歇倒计时以服务器时间偏移和规则秒数计算，只提示不自动处罚；页面恢复可见、联网恢复或旋转后重新拉取权威状态。

自动化验收使用 390×844、375 px 宽和 1024×768 等 Chromium 浏览器视口，并检查键盘与无障碍状态；这些证据必须标注为“浏览器设备模拟”，不能冒充 iPhone、Android 平板或现场真机验收。
