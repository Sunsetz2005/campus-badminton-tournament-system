# 数据库与实体关系

阶段 3 已在前两次基础迁移上追加 `phase3_authoritative_scoring`，并实际应用到开发库和 `_test` 库。

## 阶段 1 已实现

- Better Auth：`User`、`Session`、`Account`、`Verification`。
- 赛事与规则：`Tournament`、`Competition`、`Stage`、`Group`、`Court`、`RuleProfile`、`RuleProfileRevision`、`MatchRuleSnapshot`。
- 人员与报名骨架：`Participant`、`Entry`、`EntryMember`。
- 比赛骨架：`Match`、`Game`、`MatchEvent`、`ResultRevision`。
- 权限与审计：`RoleAssignment`、`OfficialAssignment`、`ScoringSession`、`AuditLog`。

首迁移创建表、枚举、外键和唯一索引；第二迁移增加非负比分/版本、A/B 不同、规则 revision 为正、成员槽位、每场唯一 `ACTIVE` 控制会话，以及提交时检查单打 1 人、双打恰好 2 名不同成员的延迟约束触发器。

开发库与测试库分离，数据库默认时间使用 `now()`。模拟种子只允许写入明确开发库或 `_test` 库，重复运行不会复制赛事、比赛、选手、角色或指派。

## 阶段 3 已实现

- `MatchSnapshot` 每场唯一，保存初始状态/哈希、当前状态/哈希、引擎版本和事件版本。
- `MatchEvent` 保存命令摘要、预期版本、前后状态与哈希、作用会话、操作者及实际角色、幂等响应。
- `Match.controlGeneration` 是控制代次权威值；`ScoringSession` 保存 token 摘要、心跳/过期、撤销原因和实际使用角色。
- `ResultRevision` 保存主裁判提交人/角色和裁判长复核人/角色，支持 `PENDING`、`RETURNED`、`LOCKED`、`SUPERSEDED`。
- 每条成功命令在同一串行化事务更新事件、快照、`Match.version`、`Game` 投影、结果修订和审计；任一步失败全部回滚。

## 阶段 4-0 已实现（赛事门户）

迁移 `20260922030854_phase4_tournament_portal`：

- `Tournament` 增加门户元数据：`subtitle`、`organizer`、`venue`、`summary`、`startDate`/`endDate`（`@db.Date` 自然日）、`posterPath`/`posterAlt`、`publishedAt`。
- 新枚举 `TournamentPhase`：`PREPARING` → `REGISTRATION_OPEN` → `REGISTRATION_CLOSED` → `RUNNING` → `FINISHED`。
- 新枚举 `NamePublicationPolicy`：`CODES_ONLY`（默认）/ `DISPLAY_NAMES`，落在 `Tournament.namePolicy`。
- `Match.publishedAt` 是**逐场公开发布边界**，并加索引 `(publishedAt, scheduledAt)`。
- 数据库级不变量：`tournaments_date_range_check`、`tournaments_poster_path_check`、`tournaments_slug_format_check`、`tournaments_published_requires_timestamp_check`。

### 两个状态维度不得合并

`TournamentStatus`（`DRAFT`/`PUBLISHED`/`ARCHIVED`）是**发布可见性**，决定赛事是否出现在公开端；
`TournamentPhase` 是**赛事生命周期**，决定它在首页落到「进行中 / 即将开始 / 已结束」哪一组。
两者分开的理由与 `lifecycleStatus`／`verificationStatus`／`outcomeType` 三维分开一致：
一个草稿赛事可以处于报名阶段，一个已结束赛事仍然必须公开可查。

`phase` 由组织者显式推进并写审计，**不按服务器当前时间推导**——与「前端不得按当前时间或比分猜测」同一条原则。

### 命名对照

本文档早期表格里的 `EventCategory`、用户提案中的 `Event`，在代码与数据库中一律是 **`Competition`**（表 `competitions`）。
它已经出现在迁移、公开 API 和追踪矩阵里，不再改名。

### 逐场发布边界

公开投影一律附加 `WHERE "publishedAt" IS NOT NULL`。赛事级 `PUBLISHED` 只表示「这个赛事可见」，
不表示「它下面每一场都可公开」。阶段 4-B 生成签表与赛程后，由发布动作统一写入该列。

### 公开投影的读取边界

`src/server/services/public-projection.ts` 会在**服务端**读取 `MatchSnapshot.state`，
但只从中取三件事实：总局分、权威胜方、被特殊结果中断的局号。
引擎状态里的发接发、站位、球员 ID、待办和抛币事实一律不进入公开 DTO。
公开读取路径不做事件重放校验（那是裁判写入路径的职责），因此不能用它替代 `loadVerifiedAggregate`。

## 业务实体

| 实体 | 责任 | 关键关系/约束 |
|---|---|---|
| Tournament | 一届赛事及公开状态 | 拥有项目、场地、时间和规则采用记录 |
| EventCategory | 男单/女单/男双/女双/混双等配置 | 关联报名、规则快照、分组和签表 |
| Participant | 参赛者私密主档 | 公开页面只能读取脱敏投影 |
| Pair | 固定双打组合 | 恰有两名不同球员；整场身份不随换边改变 |
| Registration | 个人或组合的报名和审核 | 保留提交、审核、驳回原因和版本 |
| Group / DrawSlot | 小组、种子、签位和来源 | 人工调整必须审计；晋级席位引用来源 |
| Match | 固定 A/B 对阵、状态和规则快照 | 双打比分属于组合，不属于单个球员 |
| Court / ScheduleSlot | 场地和时间窗口 | 同场地不可重叠，参与者需满足休息约束 |
| OfficialAssignment | 裁判指派和有效期 | 是主裁判操作授权条件之一 |
| RuleProfile / RuleProfileRevision | 规则模板身份与不可变版本 | 支持赛事、组别、阶段作用域和采用记录 |
| MatchRuleSnapshot | 每场解析后的完整只读规则 | 保存来源链和 `configHash`，不能随模板漂移 |
| MatchLease | 当前主记分会话、心跳和接管代号 | 每场最多一个有效写租约 |
| MatchCommand | 客户端命令及幂等结果 | `commandId` 唯一，保存载荷摘要和响应 |
| MatchEvent | 不可变业务事件 | 按比赛和版本有序追加，不物理抹除 |
| MatchSnapshot | 权威派生状态 | 与事件版本对应，可由历史重建 |
| ResultConfirmation / ResultRevision | 裁判提交、复核、锁定与追溯修订 | 保存原版本、批准链和影响评估 |
| CorrectionCase | 非普通更正申请和影响预览 | 保存原因、前后对比、批准与处置 |
| Ranking / Qualification | 排名计算和晋级来源 | 记录规则版本、输入结果和解释 |
| AuditLog | 安全和管理操作审计 | 追加式，包含操作者、时间、对象和结果 |
| ExportArtifact | 成绩册/报表生成记录 | 保存模板版本、哈希和隐私范围 |
| ImportBatch / ImportRow | Excel/CSV 导入批次和逐行结果 | 保存来源哈希、预览、幂等键及错误，不存为公开数据 |
| PublicationSnapshot | 某次公开/导出的锁定投影 | 保存字段白名单、结果版本和替代关系 |

## 阶段 1 最小数据设计

阶段 1 已按本节创建支撑登录、权限、模拟比赛和后续迁移的最小结构；阶段 2 只增加纯规则引擎，没有提前实现服务端记分事务、完整排名、报表或批量导入 UI。

| 最小对象 | 阶段 1 必要字段/约束 | 后续扩展 |
|---|---|---|
| `Tournament` | 名称、时区、状态、默认规则 revision | 发布记录、公开策略 |
| `EventCategory` | `eventCode`、组别、赛事、可选规则 revision | 编排参数、种子策略 |
| `CompetitionStage` | 类型、所属单项、规则 revision、冻结时间 | 小组/淘汰映射 |
| `RuleProfileRevision` | 不可变版本、来源、配置 JSON、`configHash`、采用状态 | 规则差异和完整验证 |
| `MatchRuleSnapshot` | 比赛 ID 唯一、解析后配置、来源链、哈希 | 阶段 2 reducer 输入 |
| `Participant` | 内部 ID、显示名、资格类别、代表队 ID | 私密资料分表 |
| `Entry` / `PairMember` | 单项/组别唯一；双打恰好两名不同成员 | 导入批次、发布冻结 |
| `Match` | A/B、阶段、规则快照、`lifecycleStatus`、`outcomeType`、`verificationStatus`、版本 | 逐分和晋级依赖 |
| `User` / `RoleAssignment` | 用户、角色、赛事范围 | 管理界面 |
| `OfficialAssignment` / `MatchLease` | 主裁判指派、唯一有效会话、代次 | 心跳和接管历史 |

三个状态维度必须分开：

- `lifecycleStatus`：排定、待抛币、进行中、暂停、结束待提交等过程。
- `outcomeType`：NORMAL、WO、RET、DSQ、ABANDONED、BYE 等结局。
- `verificationStatus`：未提交、待复核、已锁定、争议、已被修订等发布可信度。

阶段 1 初始迁移是从零创建，不操作现有真实数据库。阶段 2 只实现纯规则聚合，没有新增迁移；阶段 3 再把命令摘要、事件和权威状态快照接入事务。阶段 4—6 添加导入、排名、晋级和修订细节；阶段 7 添加 `PublicationSnapshot`/`ExportArtifact`。每次只做可回滚的增量迁移。

## 比赛权威快照的关键维度

- 固定身份：`sideA`、`sideB`，双打时各自固定两名球员。
- 比分状态：当前局、局比分、已完成局、比赛状态。
- 发接发状态：发球方、发球员、接发球员、双方逻辑左右发球区。
- 场地状态：A/B 当前物理场地端；它只在确认换边命令后改变。
- 设备视图：屏幕朝向属于设备偏好，不能写入比赛规则状态。
- 待办提示：间歇、换边、局结束等提示包含触发版本和确认状态，防止重复触发。
- 并发信息：比赛版本、当前租约、接管代号和最后确认命令。

## 历史与更正

撤销和更正不删除 `MatchCommand` 或 `MatchEvent`。普通撤销引用最近可撤销命令；特殊更正建立 `CorrectionCase`，保存原结果、新结果、原因、权限和影响图。新局已开始、结果已锁定或后续比赛已开始时，由状态门禁决定是否必须升级到裁判长处理。

删除业务数据原则上采用状态变化或受审计的软删除。具体保留期限、个人信息清理和备份策略需结合学校要求再定。

## 关系检查重点

1. 晋级签位引用上游比赛/名次来源，不能只复制名字，否则更正无法传播。
2. 一个比赛版本只能有一个权威快照；事件版本必须单调增长。
3. `commandId` 全局唯一或按明确命名空间唯一；载荷摘要用于识别同 ID 不同内容。
4. 当前有效租约需要数据库约束或事务锁保证唯一，不能只由前端按钮保证。
5. 公开查询通过单独投影/DTO 输出，禁止直接序列化 Participant 主档。
6. 双打成员在抽签发布后不能通过更新 Participant 显示名替换，成员关系需要版本/冻结约束。
7. 小组退出只改变统计资格投影；Match、比分和事件历史不能级联删除。
8. 晋级和导出必须引用已锁定 ResultRevision/PublicationSnapshot，不能读取“当前看起来最新”的可变行。

## 阶段 4-A：报名与身份（迁移 `20260924020000_phase4a_registration`）

| 变化 | 说明 |
|---|---|
| `User.systemRole`（`USER`/`SYSTEM_ADMIN`） | 平台级角色只决定能否新建赛事；不授予任何既有赛事的访问权，赛事内权限仍只看 `RoleAssignment` |
| `Tournament.regulations`、`registrationOpensAt/ClosesAt`、`nextParticipantSeq` | 规程说明、按赛事时区录入的报名窗口、赛事内选手编号序列 |
| `Competition.nextEntrySeq` | 报名单位编号 `MS-001` 递增，撤回后不复用 |
| `Participant.tournamentId`（NOT NULL）、`studentId`、`contact` | 选手按赛事隔离；`publicCode` 与 `studentId` 均改为赛事内唯一；学号与联系方式只供内部审核，不进公开白名单 |
| `EntryMember.competitionId` | `entries.competitionId` 的冗余副本，由触发器保证一致，只为让 `(competitionId, participantId)` 唯一索引兜底「同一人同项目只在一个报名单位」 |
| `Registration` | 报名申请：`PENDING/APPROVED/REJECTED/WITHDRAWN`、来源 `MANUAL/IMPORT/INVITE`、`version` 乐观并发、回执号 `R-XXXX-XXXX`、`dedupeKey`、通过后才挂 `entryId` |
| `RegistrationMember` | 报名时提交的人员信息原样保留；审核通过时解析为 `participantId` |
| `RegistrationInvite` | 邀请链接只存令牌 SHA-256 摘要与前 4 位提示；失效时间、名额与已用数 |
| `RegistrationImportBatch` | 只存内容摘要与计数，不存原文件；`(tournamentId, contentHash)` 唯一，同一文件只能导入一次 |

迁移中的数据库兜底：

- 回填：`entry_members.competitionId` 取自 `entries`；选手归属到其报名所在的**唯一**赛事，无法唯一判定时 `RAISE EXCEPTION` 中止迁移，不猜测。
- 触发器 `entry_members_scope`：成员的项目必须与报名单位一致，选手必须与项目属于同一赛事。
- 触发器 `registrations_scope`：报名的赛事与项目所属赛事一致。
- DEFERRABLE 约束触发器：单打报名恰好 1 人、双打恰好 2 人（与 `entries` 同一做法）。
- CHECK：只有 `APPROVED` 挂 `entryId` 且 `APPROVED` 必须挂；`REJECTED` 必须有原因；报名窗口开始早于截止；邀请名额为正且已用数不超过名额；导入计数自洽；姓名非空。
- 部分唯一索引 `registrations_active_dedupe_key`：学号齐全时，同一项目内进行中/已通过的报名去重键唯一（成员排序后生成，A+B 与 B+A 相同）。
- `registrations.entryId` 与 `entry_members.participantId` 外键改为 `NO ACTION`（语句末检查）：撤回时必须先解除关联再删 Entry；整赛事级联删除仍能在同一语句内完成。

身份判定规则（纯函数与服务端共用，见 `previewIdentity`）：

1. 有学号：学号命中且规范化姓名一致 → 同一人；学号命中但姓名不同 → 冲突，必须人工核对；学号未命中但存在「无学号的同名人员」→ 需人工确认；否则新建。
2. 无学号：存在任何同名人员 → 需人工确认（关联到指定人员或确认新建为同名不同人）；否则新建。
3. 姓名从不单独作为合并依据。


## 阶段 4-B：团体赛与抽签编排（迁移 `20260924120000_phase4b_team_draw` 与 `20260924120100_phase4b_constraints`）

两个迁移分开：PostgreSQL 不允许在添加枚举值（`TEAM`、`TEAM_MANAGER`）的同一事务里使用新值，所以引用新值的 CHECK 与触发器放在第二个迁移。

| 变化 | 说明 |
|---|---|
| `CompetitionKind.TEAM`、`EntryType.TEAM` | 团体赛（学院对抗）：报名单位是一支队伍 |
| `Competition.teamRubbers`（有序、可重复）、`teamRosterMin/Max`、`teamMinMale/Female` | 每场对抗的小场顺序与名单人数要求；项目默认五个小场、4—12 人、至少 2 男 2 女 |
| `Gender`；`Participant.gender`、`RegistrationMember.gender` | 性别只用于核对名单能否组成男/女/混合小场，由负责人明确填写，不从姓名或证件推断 |
| `Team`（赛事内 `code` 与 `name` 唯一） | 代表队，校内联赛中通常是一个学院 |
| `TeamManager`（`teamId`＋`userId` 唯一，冗余 `tournamentId`） | 队伍负责人绑定；只授权查看和提交本队名单 |
| `User.mustChangePassword`、`provisionedForTournamentId` | 管理员开通的负责人账号首次登录须改口令；重置口令只允许本赛事开通且无任何赛事角色的账号 |
| `Registration.teamId`、`Entry.teamId`（`(competitionId, teamId)` 唯一）、`RegistrationSource.TEAM_MANAGER` | 团体报名挂在队伍上；团体 Entry 以队伍名称显示 |
| `Draw` | 一次抽签：版本、状态（草稿/已发布/已被替代/已撤销）、赛制、算法版本、随机种子、名单快照与摘要、设置、调签记录、结果、冲突数、发布/撤销人时间与原因 |
| `Stage.drawId`、`Fixture` | 抽签发布生成的阶段与对阵；对阵两侧来源为「报名单位 / 某组第几名 / 某场胜者 / 某场负者」 |
| `Match.fixtureId`、`rubberKind`、`rubberOrder` | 个人对阵恰好一场比赛；团体对阵按小场顺序生成若干比赛，两侧待出场名单 |

数据库兜底（第二个迁移）：

- 团体项目配置 CHECK：`kind=TEAM` 与 `entryType=TEAM` 同真同假；团体项目 1—9 个小场、只能是五个单项、名单 1—30 人且男女下限之和不超过上限；个人项目不得带任何团体设置。
- 成员位上限放宽到 30；报名与报名单位的人数触发器改为：单打恰好 1、双打恰好 2（成员位不超过人数），团体在项目范围内、每人有学号与性别、男女人数达到下限（提交时检查）。
- `registrations_scope` 扩展：团体项目报名必须挂本赛事的队伍，个人项目不得挂队伍；部分唯一索引保证同一队伍在同一项目只有一份进行中/已通过的名单。
- `entries_scope` 触发器与 CHECK：报名单位类型与项目一致，团体报名单位必须挂同一赛事的队伍。
- `team_managers_scope`：负责人绑定的冗余赛事与队伍一致。
- 抽签：版本为正、随机种子至少 16 位、调签为数组；已发布必须有发布时间，已撤销必须有撤销时间与原因；每个项目最多一个草稿、一个已发布（部分唯一索引）。
- 对阵：两侧来源三选一且字段自洽；小组对阵两侧必须是确定报名单位；触发器 `fixtures_scope` 要求所属抽签/阶段/小组同一项目，「某组第几名」只能引用同一抽签更早阶段的小组，「胜者/负者」只能引用同一抽签更早（阶段, 轮次）的对阵——依赖无环。
- 比赛：小场类型与顺序成对出现且只能是五个单项；个人对阵恰好一场比赛；触发器 `matches_fixture_consistency` 要求比赛与对阵同阶段、团体项目必须是小场、个人对阵的比赛两侧与对阵已确定的两侧一致。
- 新增外键 `entries.teamId`、`registrations.teamId`、`stages.drawId`、`fixtures.sideA/BEntryId` 与对阵自引用均为 `NO ACTION`（语句末检查），整赛事级联删除可在同一语句内完成。

抽签发布在一个事务内：与报名审核共用赛事行锁 → 核对报名截止、无待审核、名单摘要一致、按保存参数重放逐字节一致 → 冻结规则修订 → 按轮次顺序写入阶段/小组/对阵 → 批量写入比赛与规则快照（来源链：赛事或项目规则 → 抽签 → 比赛）→ 冻结全部报名单位。发布不写 `Match.publishedAt`，比赛不因此对外公开。

## 阶段 4-D：团体对抗（迁移 `20260924180000_phase4d_team_ties` 与 `20260924180100_phase4d_constraints`）

同样分成两个迁移：新枚举 `MatchSide`、`LineupSource` 的值不能在创建它们的同一事务里使用。

| 变化 | 说明 |
|---|---|
| `RegistrationMember.rubberKinds`、`EntryMember.rubberKinds` | 报项：队员可参加的小场类型；审核通过时从名单复制到报名单位；个人项目必须为空 |
| `FixtureLineup`（`fixtureId`＋`side` 唯一；`source`、`version`、提交人与时间） | 一方在一场对抗的出场名单表头；版本号防止覆盖他人修改 |
| `MatchPlayer`（`matchId`＋`side`＋`slot` 唯一、`matchId`＋`participantId` 唯一） | 团体小场的上场队员 |
| `Fixture.lineupsRevealedAt` | 双方交齐的时刻：此前互相看不到，此后锁定 |
| `Fixture.winnerEntryId`、`decidedAt` | 对抗胜负，由已锁定小场推导，结果重开时撤回 |
| `Match.notPlayedAt` | 淘汰赛胜负已定后尚未开始的小场「未进行」（不是弃权、不记比分） |
| `Group.ranking`、`rankingConfirmedAt`、`rankingConfirmedByUserId` | 裁判长确认的小组名次（含抽签顺序与说明） |

数据库兜底（第二个迁移）：

- 报项：只能是五个单项；男队员不能报女单/女双、女队员不能报男单/男双；没有性别不能报项。团体名单与报名单位的人数触发器增加：每人至少报 1 项、报项属于本项目的小场、每种小场都有足够的报项队员（单打 1、双打 2、混双 1 男 1 女）；个人项目成员不得带报项。
- **迁移默认值**：4-B 时已有的团体名单没有报项，迁移按性别给每名队员填入本项目全部可报的小场。这不代表负责人的选择；新提交的名单必须由负责人勾选。
- `matches_fixture_consistency` 收紧为所有抽签生成的比赛（含团体小场）两侧都必须与对阵两侧一致；迁移先回填 4-B 时留空的小场两侧。
- `match_players_scope`：只属于团体小场；报名单位等于该侧队伍；队员在队伍名单里、报了该项、性别相符；成员位不超过单打 1、双打 2；小场一旦开始（版本 > 0）不能增删改。`match_players_exact_count`（提交时检查）：每侧要么 0 人，要么恰好单打 1 人、双打 2 人，混双必须一男一女。
- `fixture_lineups_scope`：只属于团体对抗，报名单位等于该侧已确定的队伍；版本 ≥ 1。
- 对阵：胜者只能是两侧之一，胜者与决出时间成对；名单公开的前提是两侧都已确定。
- 比赛：「未进行」只能是从未开始的团体小场。小组：名次与确认时间成对。
- 外键：`fixture_lineups.entryId` 为 `CASCADE`（名单依附报名单位；报名单位在抽签发布后冻结，应用内不会删除，整赛事删除时随之级联），其余新外键为 `NO ACTION` 或随比赛/对阵级联。

结算在计分命令的同一个 Serializable 事务里完成：裁判长 `CONFIRM_RESULT` 或 `REOPEN_RESULT` 一个团体小场后，按全部小场的锁定事实重新推导「未进行」、对抗胜负与下游对阵两侧（同步下游小场两侧、作废下游已交名单）；若下游对阵已有比赛开始，抛出 `downstream_started`，整条命令回滚。

## 阶段 4-C：赛程与裁判排班（迁移 `20260925120000_phase4c_schedule` 与 `20260925120100_phase4c_constraints`）

| 变化 | 说明 |
|---|---|
| `Court.active`、`sortOrder` | 场地关闭后不能再排新比赛；已排在上面的比赛在检查中为硬冲突（不自动移动） |
| `ScheduleConfig`（每赛事一行） | 个人项目/团体小场预计时长、换场时间、淘汰赛每场对抗占用场地数、出场名单截止提前量；缺省用项目默认（30/25/5/2/30） |
| `ScheduleDay`（`tournamentId`＋`day` 唯一） | 比赛日与当天开放时段（赛事时区下的分钟数） |
| `ScheduleSlot`（`matchId` 唯一） | 草稿：覆盖一场比赛的已发布安排（场地、开始、预计时长、主裁判、预计标记）；没有草稿行的比赛沿用已发布值；发布后清空 |
| `SchedulePublication`（`tournamentId`＋`version` 唯一） | 发布版本：完整快照、差异（新增/调整/撤下/换裁判/新公开/吊销会话）、确认过的警告、说明 |
| `Match.scheduledEndAt`、`scheduleEstimated` | 计划结束（开始＋预计时长）；「接上一场之后」的预计时间标记。实际开始/结束仍是 `startedAt`/`endedAt` |
| `FixtureLineup.submittedLate` | 截止后由管理员代交 |
| `Competition.teamMaxRubbersMale/Female` | 团体对抗每人最多出场小场数（按性别，为空不限） |

数据库兜底（第二个迁移）：计划结束晚于计划开始、预计标记必须有计划时间；比赛与草稿行的场地必须属于同一赛事；**已开始（版本 > 0 或离开待开赛）的比赛不能改计划时间、结束或场地**（触发器）；设置取值范围；比赛日开始早于结束；草稿场地与开始时间成对、时长 5—300 分钟；发布版本 ≥ 1 且快照/差异/警告的 JSON 形状固定；逾期提交只能是管理员代交；`match_players_tie_limit`（提交时检查）同一队员在同一对抗里的出场数不超过本项目按性别的上限。

草稿与已发布分开存放，是为了让编排中的改动不影响裁判的「我的执裁」和公开赛程；已发布安排直接写在 `Match` 与 `OfficialAssignment` 上，裁判端与公开端不需要理解草稿。休息间隔按 2026-09-25 用户决定不建模。


## 阶段 6：成绩、名次与晋级（迁移 `20260927120000_phase6_results`）

- `Match.resultSource`（`LIVE` / `RESULT_ONLY`）与 `ResultRevision.source`：仅结果记录只有逐局结果修订，没有记分事件。触发器拒绝向 `RESULT_ONLY` 比赛写入 `match_events`，也拒绝把已有事件的比赛改成 `RESULT_ONLY`；CHECK 禁止团体小场补录。退回或重开后比赛回到 `LIVE`、未开始，修订历史保留。
- 个人项目对阵复用 `Fixture.winnerEntryId`：由已锁定结果推导，随重开撤回；胜者/负者签位与团体对抗共用 `setFixtureSide`/`propagateFixtureResult`。
- `Group.ranking`（个人项目）保存方案键与版本、名次顺序、并列组、裁定依据、排除决定与计入的比赛。
- `RankingExclusion`：裁判长逐组的排除决定（原因非空，名次确认后不能改）。
- `StandingsPublication`：名次榜单发布版本（快照与内容摘要，版本 > 0），摘要与当前内容不同即「需重新发布」。
- `ResultDisposition`：更正被阻止时的人工处置登记（`MAINTAIN` / `OFFLINE_RULING`、原因、阻止项），只追加。
