## 3. 检查点A：先补失败用例，再修领域边界

### RV3-001：间歇/决胜局换边重复触发

检查 `src/domain/rules/match-engine.ts` 的 `applyRally`、`addObligation`、`removeObligation`、`applyReplacement`。

当前按任意一方等于阈值触发，处理后待办会被移除。请先复现：

1. 传统21分制，11:0完成间歇，B得分成11:1：不得重新产生间歇。
2. 单局21分及三局赛的决胜局，首次到阈值后完成间歇与实际换边，再变11:1：不得再换边。
3. 领先方已12分，另一方追到11分：不得再次产生阈值事项。
4. 3×15配置的8分阈值覆盖同样场景。
5. 跨局、换边后撤销、手动比分更正、恢复历史后的阈值行为。

普通得分应按本局领先分首次跨越阈值处理；更正和撤销要结合已执行事项的历史。不能只把相等改为大于等于，也不能只看本次得分一方等于阈值。

### RV3-003：暂停期间清空待办后恢复会卡住

检查 `finishObligationPhase`、`PAUSE_MATCH`、`RESUME_MATCH` 及界面待办入口。

复现：进入规则待办→暂停→确认全部间歇/换边事项→恢复。最终必须进入可继续比赛的正确相位，不能得到 `OBLIGATIONS_PENDING` 加空数组。

首选保留暂停时可以核对现场事项的能力，正确更新恢复目标相位。也要测试只处理部分待办时不会错误恢复。不能只改前端隐藏按钮。

### RV3-006：比分更正沿用旧待办

检查 `scoring-workbench.tsx/previewCurrentAction` 与 `match-engine.ts/applyReplacement`。

修改分数后直接携带旧 `pendingObligations` 会与服务器校验冲突。请覆盖10:8→11:8、11:8→10:8、已完成阈值事项后更正、跨局末误点等。

让服务器根据用户更正意图和历史执行事实生成完整预览。浏览器不再承担独立的一套竞赛推导算法；不要放松领域校验来迁就旧请求。必要的接口调整保持预览和最终提交一致，版本冲突必须安全拒绝。已实际换边不能无声回滚。

### 在修改引擎前先解决历史兼容

`match-state-service.ts/loadVerifiedAggregate` 会从初始状态重放所有旧事件，并和存储快照比较。直接修改引擎输出或状态形状可能使已有比赛无法读取。

请先用现有数据结构构建可重放历史夹具，明确旧引擎版本、新事件版本、快照升级的方案。支持旧版本语义重放或采用明确受控的升级流程；不能只增加 `MATCH_ENGINE_VERSION` 常量却仍让所有旧事件走新语义。不能删事件、关闭哈希校验或擅自清空模拟库。

若方案确需不可逆数据操作，停在该操作前请求批准，继续其他独立、安全的代码与测试工作。

## 4. 检查点B：修复真实执裁路径，而不是只让接口通过

### RV3-002：抛币双方选择不完整

`scoring-workbench.tsx/PhaseActions` 当前快捷按钮写死一部分场地及负方选择。引擎已经支持不同组合，请保留正确引擎，改为紧凑的联动表单：

确认胜方 → 胜方选先发/先接或具体场地端 → 负方选择剩余类别 → 明确摘要 → 确认提交 → 本局首发/首接设置。

所有选项绑定实际A/B与场地端，取消不提交，刷新不重新随机。不必增加抛币动画，更不能以动画替代选择。

浏览器测试必须覆盖A/B均可获胜、服务类别后负方选两端、场地类别后负方选先发或先接，验证最终发球方、物理端与事件。领域测试支持这些选项不等于页面可操作。

### RV3-004：本局/全场结束后的误点撤销入口

`court-console.tsx` 的减分按钮被 `activePlay` 限制，结束阶段没有可用入口；领域层已有未提交最后得分的撤销能力。

在 `GAME_COMPLETE`、`MATCH_COMPLETE_PENDING_SUBMISSION` 等适用状态增加“撤销刚才结束本局/本场的得分”入口，仍走服务端预览、原因、确认。不要无条件放开所有减分按钮。

验证：结束前20:19误点21:19能撤回；单局赛亦然；确认实际换边后撤销需要现场端位核对；已开始下一局/已提交/已锁定不能绕过现有控制。

打开“次要操作与记录”后也要能找到相关入口，但赛末关键纠错不应只靠工程人员知道API。

## 5. 检查点C：记分回执、时间和网络语义

### RV3-005：旧命令回执不能覆盖较新比分

检查 `refresh`、`reconcilePendingCommand`、`submitEnvelope`，以及服务端重复命令与查询历史回执路径。

统一版本单调的状态接收逻辑：页面已v10，原命令回执v8仅能确认该命令曾接受，不能把比分/站位改回v8并显示“最新”。不要只更新 `latestVersionRef` 而仍写入旧 `body.state`。

补故障注入：先取v10再拿v8；重复命令回执；旧设备恢复时已被接管。低版本回执可以消除原命令未知状态，但权限必须来自有效控制状态，不能把旧设备重新变成可写。

### RV3-008：来源不明确的HTTP错误不能一律丢弃原命令

当前HTTP错误路径会删除待确认数据。请区分协议明确保证未执行的业务拒绝，与网络/代理造成的不确定回执。对已可能提交但收到502等场景，保留原ID、进入UNKNOWN并对账；在解决前不允许生成新的记分命令。

这条是待故障注入验证的可靠性风险，不是已证实线上重复计分。不要按4xx/5xx粗暴判断，读取真实接口错误契约。覆盖提交后响应损坏、超时、代理502、确定业务拒绝，确保无假成功、无重复分、无卡死。不要为了演示测试而真连外部代理或生产服务。

### RV3-007：实际结束时刻不随提交/复核改写

检查 `scoring-command-service.ts/updateProjections`。最后得分10:00、提交10:05、复核10:10，实际结束仍应是10:00；提交和复核各有自己的时间。

按真实业务转换维护结束时刻，并明确重开及恢复比赛时的语义。加入固定时钟集成测试。未实际开赛的弃权/轮空不能伪造成运动结束。未来休息时间计算要用正确口径。
