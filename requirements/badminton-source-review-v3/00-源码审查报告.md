## R3-001｜P1：阈值间歇与换边会重复产生

**证据：源码路径确认＋提取逻辑复现；原项目完整回归待执行。**

位置：[src/domain/rules/match-engine.ts](https://github.com/Sunsetz2005/campus-badminton-tournament-system/blob/84a159218b300de333e101da5af6ea8d51d3bacb/src/domain/rules/match-engine.ts)，`applyRally`、`addObligation`、`removeObligation`、`applyReplacement`。

现有判断为：

```ts
scoreA === state.ruleConfig.intervalAt || scoreB === state.ruleConfig.intervalAt
```

决胜局换边也使用双方任意一方当前分数等于阈值的判断。`addObligation` 只对当前 `pendingObligations` 去重；确认后 `removeObligation` 删除待办，下一分可以用同一个 ID 再创建。

复现流程：单局 21 分，或三局赛决胜局，A 到 11:0；处理间歇并确认实际换边；B 赢下一回合成为 11:1。因为 A 仍等于 11，重新生成 INTERVAL 和 CHANGE_ENDS。再次确认会把物理场地端换回去。

普通三局赛第一局会重复间歇；3×15 决胜局在 8:0→8:1 也出现相同问题。提取复现的四个配置均重建了同 ID 的已处理待办。

修复要求：识别本局首次跨越阈值与已发生/已确认事实，并处理撤销、完整更正、实际换边核对之间的关系。不能仅改成 `>=`，也不能仅在 UI 隐藏弹窗。更正比分时也要考虑阈值历史，不能简单依当前分数重新生成或抹掉义务。

新增测试应明确断言“已处理后下一分不再生成”，不要用无条件 `clearObligations` 循环把重复处理吞掉。需覆盖领先方保持在阈值、另一方后来达到阈值、对称 B 方、不同预设和独立间歇/换边阈值。

**历史兼容：** 当前事件重放会重新执行命令并比较完整快照。改变此逻辑可能使旧记录的重放结果不一致。必须设计有版本的兼容/迁移，保留历史证据；不能删除历史记录或关闭哈希/重放校验。

## R3-002｜P1：旧命令回执可能覆盖已取得的新快照

**证据：跨前后端源码路径确认；原浏览器竞态待注入复现。**

位置：[src/components/scoring-workbench.tsx](https://github.com/Sunsetz2005/campus-badminton-tournament-system/blob/84a159218b300de333e101da5af6ea8d51d3bacb/src/components/scoring-workbench.tsx) 的 `reconcilePendingCommand`、`submitEnvelope`、`refresh`；[src/server/services/scoring-command-service.ts](https://github.com/Sunsetz2005/campus-badminton-tournament-system/blob/84a159218b300de333e101da5af6ea8d51d3bacb/src/server/services/scoring-command-service.ts) 的 `getScoringCommandResult` 和重复命令返回分支。

`refresh` 有较旧版本防护，但命令查询/提交成功后只是把 `latestVersionRef` 取最大值，然后无条件把 `body.version` 和 `body.state` 写入界面快照。查询接口返回保存于事件中的历史响应，并非查询时的最新比赛状态。

页面恢复流程先 `refresh(true)`，再 `reconcilePendingCommand()`。因而可以先获取 v12，再按原 commandId 找回 v8 回执，然后把 UI 写回 v8，并显示已同步。下一次轮询可能恢复，但不能依赖其掩盖短暂错误；服务端版本检查通常会拒绝用旧版本提交的新命令，并不代表界面允许倒退。

修复要求：分离“该命令是否已成功处理”和“应用最新权威状态”；所有入口共同使用单调版本策略。历史回执可清理对应待确认项，但不得覆盖较新快照，也不能错误更新新鲜度、控制权或过期状态。

## R3-003｜P1：HTTP 错误和异常成功响应丢失待确认命令

**证据：客户端错误处理路径确认；需要代理/故障注入验证后果。**

位置：[src/components/scoring-workbench.tsx](https://github.com/Sunsetz2005/campus-badminton-tournament-system/blob/84a159218b300de333e101da5af6ea8d51d3bacb/src/components/scoring-workbench.tsx) 的 `responseJson`、`submitEnvelope`。

当前所有非 2xx 都包装成 `ApiRequestError`。捕获到该错误后无条件删除 pendingKey，包括 500/502/504；普通错误分支可能恢复为 SYNCED。HTTP 5xx 并不能证明请求从未落库，例如数据库已提交后网关返回错误。另一个路径是在未验证成功响应形状前就清理 pending，随后访问异常 body 又出错。

修复要求：明确区分有结构、可核对 commandId 的确定拒绝，与结果未知。对网络超时、可疑 5xx、无效响应保留原命令，查询或重试相同 ID；对有效明确拒绝才退出对应待确认流程。成功响应须验证 commandId、version、state 及状态后再清理。不得因为 UI 解锁需要直接删除待确认信息。

## R3-004｜P2：结束时间被提交和复核时间覆盖

**证据：服务端更新路径确认；数据库生命周期测试待执行。**

位置：[src/server/services/scoring-command-service.ts](https://github.com/Sunsetz2005/campus-badminton-tournament-system/blob/84a159218b300de333e101da5af6ea8d51d3bacb/src/server/services/scoring-command-service.ts) 的 `lifecycleProjection`、`updateProjections`。

`ENDED_PENDING_SUBMISSION` 或 `SUBMITTED` 时，每条命令更新都把 `endedAt` 赋成新的 `now`。CONFIRMED 也投影为 SUBMITTED，所以比赛 10:00 结束、10:05 提交、10:10 复核，会把结束时间逐步覆盖为后两个时间。

修复要求：区分实际开赛/结束时间与提交/复核时间。提交复核不能改变已确认的实际比赛结束时刻；撤销误判终场、重开、恢复比赛及特殊结果应有明确语义。后续时长、最短休息排程会依赖这些数据，不能使用审核时间替代实际结束时间。

## R3-005｜目标设备高优先级：普通局域网 HTTP 与 UUID 能力不匹配

**证据：源码调用及文档路径确认＋浏览器能力资料；未做真实手机验证。**

位置：[src/components/scoring-workbench.tsx](https://github.com/Sunsetz2005/campus-badminton-tournament-system/blob/84a159218b300de333e101da5af6ea8d51d3bacb/src/components/scoring-workbench.tsx) 的 `deviceId` 和 `makeEnvelope`，直接调用 `crypto.randomUUID()`；[docs/knowledge-base/07-使用部署/本地启动与手机访问.md](https://github.com/Sunsetz2005/campus-badminton-tournament-system/blob/84a159218b300de333e101da5af6ea8d51d3bacb/docs/knowledge-base/07-%E4%BD%BF%E7%94%A8%E9%83%A8%E7%BD%B2/%E6%9C%AC%E5%9C%B0%E5%90%AF%E5%8A%A8%E4%B8%8E%E6%89%8B%E6%9C%BA%E8%AE%BF%E9%97%AE.md) 描述通过 `http://Mac局域网IP:3000` 访问。

MDN 标明 `Crypto.randomUUID()` 限安全上下文。电脑 localhost 的可用性不证明手机用局域网 IP 的明文 HTTP 也可用。在缺少该方法的环境中，获取设备ID或创建命令会失败。

修复要求：明确开发演示和实际执裁的部署边界；实际执裁优先使用可信 HTTPS。进入可写界面前检测所需能力，并给出可理解的提示。若提供兼容方案，使用经过审查的 UUID 实现和安全随机来源，不用 Math.random，不关闭浏览器安全策略、认证或 CSRF 来绕过问题。需同时检查认证来源配置，不在没有真机时宣称手机已验收。

外部核验资料（不属于仓库自身证明）：
- [MDN Crypto.randomUUID](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID)
- [MDN Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)

## 后续核验项，不伪装成已测出的事故

### 本地存储容错

`scoring-workbench.tsx` 多处在无保护或 try 之外读取、JSON.parse 或写入存储。建议注入损坏记录、写入被拒绝、不同标签页/不同登录用户及控制权更换场景；根据实际结果补防护。不要把不能解析的待确认命令直接清空并显示同步成功，应保留可安全核对的信息并进入受控恢复。

### 轮询与重放成本

[src/server/services/match-state-service.ts](https://github.com/Sunsetz2005/campus-badminton-tournament-system/blob/84a159218b300de333e101da5af6ea8d51d3bacb/src/server/services/match-state-service.ts) 的读取路径先获取比赛行锁，再加载所有事件重放，即使 afterVersion 最终匹配也已完成这些工作。客户端通常每 2 秒轮询；`replayMatch` 又会通过事件创建路径复制已有历史。存在长比赛及多只读端的性能风险，但本次没有量化延迟或并发吞吐。先测量再优化，不直接删除锁或完整性保护。

### 视觉改造

本轮读了实际 JSX 和投影逻辑，没有独立运行浏览器，也没有取得新的实际界面截图。因此不宣称某个像素、留白或移动端溢出已被本轮目测确认。建议在保留正确行为的基础上，把现有场地组件重排为场地→三按钮→大比分→加减分，并由浏览器截图验证。
