## 4. 检查点 A：先复现修复正确性和可靠性

### R3-001：间歇和换边同一阈值只能按本局规则发生一次

检查 applyRally / addObligation / removeObligation / applyReplacement。当前源代码只判断 A 或 B 是否恰好等于阈值，确认后删除待办，后续得分又可能重建同一义务。

必须先在原项目追加失败测试：
- 单局21：11:0确认间歇及换边后，B得分到11:1，不得再生成同一间歇或换边。
- 三局21第一局：11:0处理间歇后到11:1，不得再间歇。
- 三局21决胜局、3×15决胜局8分：同样验证。
- 首次阈值处理后，领先方继续得分，另一方稍后到阈值，也不能重复。
- B方领先的对称用例。

不要用自动 clearObligations 循环替代“义务不应生成”的断言。

根据状态模型设计首次跨越、已触发/已确认事实和物理场地核对机制；完整更正、撤销最近一分、已经实际换边必须协调。不能只把 == 改成 >=，不能仅前端过滤。规则配置按本场快照，不写死11或8。

重要：检查 MATCH_ENGINE_VERSION、事件 engineVersion、replayMatch、snapshot/hash 的兼容。修复后不能使旧事件在新代码中无说明地重放失败。提出最小明确的版本化/迁移策略，保留原证据；需要修改真实历史数据时停止并请求批准。不得删除事件、重置比赛库或关闭完整性校验来让测试变绿。

### R3-002：历史命令回执不得使比赛状态降版本

检查 refresh、reconcilePendingCommand、submitEnvelope 与 getScoringCommandResult。

将“命令结果已知”与“界面采用哪个权威快照”分开。所有响应入口使用统一、可测试的版本规则，不能只更新 latestVersionRef 的最大值却仍写入低版本 state。

必须测试：先刷新得到v12，再查询未决的旧命令得到v8。旧命令应被正确核销，但界面版本和比分不得倒回v8，也不得将过期数据标为新鲜。覆盖重复POST回执、刷新、可见性/旋转、接管和网络乱序。

### R3-003：5xx和异常成功响应维持原命令的可对账性

检查 responseJson、submitEnvelope、pending存储。

对可核实的明确拒绝和结果未知分别处理。服务端已提交后收到502/504、5xx无法确定落库、200但无有效JSON或响应结构不符，都不能立即删除pending并允许新命令。

先验证响应与原 commandId 相符、version/state有效，再核销。未知时保留原ID和足够的恢复信息，查询或按原ID重试；不能自动生成新ID补发同一分。

如新控制会话产生后旧命令已不可能被原会话接受，设计有明确服务器证据的恢复流程，不能永远锁住，也不能静默抹除。保留控制代次保护，不让旧设备恢复写权限。

补本地存储容错测试：JSON损坏、setItem抛错、不同标签页/不同用户状态隔离。解析失败应安全只读并提供恢复路径，不能崩溃或假成功；不要把令牌迁移到不受控的共享存储。

### R3-004：实际结束时间与提交复核时间分离

检查 updateProjections。只在语义正确的实际终场转换记录 endedAt，提交与复核不覆盖实际结束时间。利用/完善结果修订的提交与复核时间，不需要大改现有结构时不要新增重复字段。

测试受控时钟：10:00比赛结束、10:05提交、10:10确认，endedAt仍为10:00。补撤销终场、退回更正、真正恢复比赛、重新结束、WO/RET/BYE的时刻语义，不能虚构未发生的实际开赛。

### R3-005：手机和平板的实际访问条件

检查 deviceId / makeEnvelope 的 crypto.randomUUID 及部署文档。

电脑localhost和手机通过LAN IP的普通HTTP不是同一安全上下文。检查 isSecureContext 与所需API；实际执裁优先可信HTTPS，缺能力时给明确提示和只读状态，不让按加分时才抛原始异常。

确有本地演示兼容需要时使用经审查的安全随机UUID方案，禁止 Math.random、禁用浏览器保护、关闭认证或CSRF。核实认证来源及跨设备配置，不能把只修改UUID当作整个HTTPS和登录部署问题都解决了。

真机没有连接时，只记录浏览器模拟与能力注入测试；不能说已经完成iPhone/iPad验收。
